This simplifies crash recovery and auditing.\n\n## Retries and Backoff\n\nWe adopt exponential backoff with jitter. The delay for the `n`-th retry (1-indexed) is:\n\n```\ndelay = base_delay * (2 ** (n - 1)) + random(0, jitter)\n```\n\nwhere `base_delay` is `retry_delay_ms` and `jitter` is `base_delay * 0.2`. The maximum delay is capped at `base_delay * 2 ** (max_retries - 1) + jitter`.\n\nWhen a handler raises an exception, we increment `retry_count` and update `last_error`. The task remains in `enqueued` status (or `running` if we want to track the current attempt) and will be picked up again after the backoff period. The `scheduled_at` field is updated to `now() + delay`.\n\nWe do **not** allow a task to be retried indefinitely; once `retry_count` reaches `max_retries`, the task is marked `dead` and will never be picked up again.\n\n## Crash Recovery\n\nBecause SQLite is ACID and we always write under a single connection, a crash can only leave the database in a consistent state. The only possible inconsistency is a task that was marked `running` but whose handler crashed before we could update the status. Such a task will still be visible to other workers because we never delete it; we only transition its status.\n\nWe handle this by periodically scanning for tasks with `status = 'running'` and `scheduled_at <= now()`. If any are found, we reset their status to `enqueued` and clear `last_error`. This is done in a background thread or as part of `taskq.work()` when no runnable tasks are available.\n\nWe also ensure that any task that was claimed (status changed to `running`) but not yet executed will be re-claimable. The claim is purely an `UPDATE` that changes `status` from `enqueued` to `running`; if the process dies before the handler runs, the row remains `running` and will be reset on the next recovery scan.\n\n## Failure Modes and Handling\n\nWe considered several failure modes and designed the system to handle each:\n\n1. **Process crash mid-task** – The task remains in `running` status. Corruption is extremely unlikely and would require manual intervention.\n\n3. **Worker thread deadlock** – We use thread-local storage for the SQLite connection, ensuring each thread has its own connection and never competes for locks. The only shared resource is the database file, which SQLite handles safely.\n\n4. **Handler raising an exception** – The exception is caught, `retry_count` is incremented, `last_error` is stored, and the task is scheduled for later retry with backoff.\n\n5. **Duplicate enqueue of the same logical job** – We treat each `rowid` as a distinct task. If the same logical job is enqueued twice, both will be processed independently. To avoid duplicate work, callers should use a unique `name` per logical job and ensure they only enqueue once per `name`. The `stats()` function can help operators see how many tasks are pending for each name.\n\n## Trade-offs Rejected\n\nWe considered several alternative designs and rejected them for the following reasons:\n\n- **Using a separate in-memory queue with periodic sync to SQLite** – This would introduce a window where tasks could be lost if the process crashes before the sync runs. SQLite’s row-level locking is sufficient for our single-process, multi-threaded use case.\n\n- **Allowing tasks to be cancelled** – Cancellation would require additional state and could lead to inconsistent runs. The spec explicitly excludes cancellation.\n\n- **Using a priority queue** – Priority would require more complex scheduling and could lead to starvation. The spec does not require priority, and we want simplicity.\n\n- **Storing payloads as binary blobs** – JSON is sufficient for our use case and keeps debugging easier.\n\nWe also rejected the idea of having a separate \"dead\" table for failed tasks; we keep everything in one table to simplify recovery and auditing.\n\n## Summary\n\nThe design provides a simple, durable, and thread-safe task queue using only SQLite and the standard library. Tasks are enqueued with a name and payload, optionally scheduled for later execution. Workers claim tasks atomically, run handlers, and on failure retry with exponential backoff.
