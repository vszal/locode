All writes are wrapped in a single transaction to ensure that claiming, updating state, and recording runs are atomic. Workers loop over `SELECT task_id, payload, handler_name FROM tasks WHERE state = 'pending' ORDER BY created_at LIMIT 1 FOR UPDATE SKIP LOCKED`, which gives them a fair, lock-free way to grab the next task without blocking others. If a worker crashes while holding a task, the transaction is rolled back, the `state` column remains `running`, and the scheduler will see that the task has exceeded its retry limit and will move it to `failed`. No task can be stuck forever because the scheduler runs periodically (or can be triggered manually) to clean up any `running` tasks that have been idle for longer than `max_retries * base_delay` seconds.\n\nAdditionally, the `task_runs` table records every attempt, so an operator can reconstruct the full history of a failed task by querying `SELECT * FROM task_runs WHERE task_id = ? | Worker crashes while holding a task      | Transaction rolls back; scheduler moves task to `failed` after retries   |\
| Database corruption                      | SQLite's journal mode ensures atomicity; on restart, `init` recreates tables and reclaims any orphaned tasks |\

| Race between two workers claiming the same task | `FOR UPDATE SKIP LOCKED` ensures only one worker can grab the row    |\

Adding a consensus layer would increase complexity and latency, and the use case (single machine, multiple workers) does not require it. The risk of split-brain scenarios is mitigated by keeping all state in a single SQLite file.\n\n2. **Priority queues**: Implementing priority would require either a heap data structure or a separate table with a priority column, which would complicate the schema and the locking strategy. Instead, we use a simple `delay` parameter that specifies a fixed number of seconds until the task should be claimed. This keeps the API simple and the implementation straightforward.\n\n5. **Web UI**: A web interface would require a separate server process and a database schema for user sessions and task history. Since the spec explicitly excludes cross-machine coordination and a web UI, we omitted it to keep the library focused on the core reliability guarantees.\n\n6. **Multiple database backends**: Supporting PostgreSQL or other databases would increase the codebase size and introduce additional configuration options. SQLite is sufficient for the intended use case and keeps the library lightweight and easy to deploy.\n\nBy rejecting these features, we keep the design simple, testable, and robust against crashes, which aligns with the primary goal of taskq: reliable in-process task processing.\n"}}
