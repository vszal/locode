{"name": "write_file", "args": {"path": "DESIGN.md", "content": "# taskq Design Document\n\n## Overview\n\n**taskq** is a durable, in-process task queue for Python 3.10+. It provides a simple API for enqueuing background work and processing it reliably, surviving crashes of the host process. It is deliberately **not** a distributed system: one machine, one SQLite file, one or more worker threads inside the same process.\n\n### Core Guarantees\n\n- **Durability**: Nothing is lost if the process is killed mid-run. All state is persisted to SQLite.\n- **Atomic claiming**: A task can be executed by at most one worker thread at a time.\n- **Crash recovery**: A worker that is killed (SIGKILL, power loss) must not leave a task stuck claimed forever — the task becomes runnable again.\n- **Backoff retries**: Retries do not hammer a failing dependency; successive attempts back off.\n- **Duplicate prevention**: Enqueueing the same logical job twice by racing callers does not result in duplicate work.\n- **Observability**: Operators can query how many tasks are pending, running, failed, and dead.\n\n### Scope\n\n- **In scope**: Named tasks with JSON-serializable payloads, scheduled execution (\"run this in ten minutes\"), retry logic with exponential backoff, crash recovery, thread-safe worker pool, and basic metrics.\n- **Out of scope**: Cross-machine coordination, priority classes, task cancellation, scheduled cron expressions, and a web UI.\n\n---\n\n## Public API\n\nAll public functions and classes are documented here. in `handlers` is unique.\n- **State machine**: Tasks progress through `pending → running → (completed|failed) → (dead|retry)`. No task can be in `running` and `pending` simultaneously.\n- **Deduplication**: If a task with the same `idempotency_key` already exists in `pending` or `failed` state, the new enqueue is ignored (no new row is created).\n- **Scheduled tasks**: Tasks with `scheduled_at > NOW()` are never claimed until their time arrives (see Claiming section).\n\n---\n\n## Retries and Backoff\n\n### Retry Policy\n\n- **Maximum attempts**: 5 (including the initial attempt). After the fifth failure, the task is marked `failed` and **not** retried further.\n- **Backoff strategy**: Exponential backoff with jitter.\n  - Base delay: 1 second.\n  - After each failure, delay = `base * (2 ^ attempt) + random(0, 0.5 * base)`.
  - Example delays: 1s, 3s, 7s, 15s, 31s (with jitter).
- **State on retry**: When a task fails and is scheduled for retry, its `state` is set to `failed`, `attempt` is incremented, and `last_error` is stored. The task remains in the `failed` state until it is claimed again (which happens automatically by the queue's scheduled task worker).

### Implementation Details\n\n- The `Queue` maintains a background thread (or uses `sqlite3`'s `SELECT ... FOR UPDATE` with a `WHERE scheduled_at <= NOW()` clause) that periodically scans for tasks that have exceeded their scheduled time and are in `failed` state. Those tasks are then re-queued as `pending` with the updated `attempt` count.\n- The `Worker` does **not** retry on its own; it only claims and runs. Retries are driven by the queue's scheduled task worker.\n- **No hammering**: Because of the exponential backoff, a failing external service will not be hammered. The queue will wait longer between attempts, giving the service time to recover.\n\n### Edge Cases\n\n- **Task fails on the first attempt**: `attempt` = 0, `state` = `failed`. The queue will schedule a retry after 1 second (with jitter).\n- **Task fails on the fifth attempt**: `attempt` = 4, `state` = `failed`. No further retries; the task remains `failed` and is visible in `stats.failed`.\n- **Task is completed successfully**: `state` = `completed`, `attempt` is left as-is (usually 0). No further action.\n- **Task is marked dead**: `state` = `dead`. No retries ever occur.\n\n---\n\n## Crash Recovery\n\n### Problem Statement\n\nIf a worker thread is killed (e.g., SIGKILL, power loss), any task it has claimed could be left in a `running` state forever, making it impossible for other workers to pick it up. The design must guarantee that **no task is ever stuck claimed** after a crash.\n\n### Solution: Atomic Claim with Automatic Release\n\n- **Claiming is atomic**: The `claim(task_id)` method uses a `SELECT ... FOR UPDATE` on the `tasks` row, setting `state = 'running'` and `updated_at = NOW()`. This ensures that only one worker can successfully claim a task at a time.\n- **Crash handling**: If a worker crashes while a task is `running`, the task remains in `running` state. However, the queue's **scheduled task worker** (or a periodic housekeeping thread) runs a cleanup query:\n\n  ```sql\n  UPDATE tasks\n  SET state = 'pending', updated_at = NOW()\n  WHERE state = 'running' AND updated_at < NOW() - 5*60;  -- 5 minute stale threshold\n  ```\n\n  This query finds any `running` tasks that have been in that state for more than 5 minutes (a generous window to avoid false positives) and resets them to `pending`. The `5*60` seconds threshold is chosen to be long enough that a normal worker would have completed its work, but short enough that a crashed worker will not permanently block the task.\n\n- **Why 5 minutes?**\n  - Throughput target is modest (hundreds per second), so a typical task should complete well under a minute.\n  - 5 minutes gives a huge safety margin against transient slowdowns while still quickly recovering from crashes.\n  - The threshold is configurable in the future (e.g., via an environment variable), but for this design we fix it at 5 minutes.\n\n### Guarantees\n\n- **No task is ever permanently stuck**: After any crash, the housekeeping thread will eventually reset `running` tasks to `pending`.\n- **No duplicate execution**: Because claiming is atomic, two workers cannot claim the same task simultaneously.\n- **Correct retry behavior**: When a `running` task is reset to `pending`, its `attempt` and `last_error` are preserved, so the next run will continue from where it left off (or retry if it failed).\n\n---\n\n## Failure Modes and How the Design Handles Them\n\n| Failure Mode                              | Description                                                                 | How the Design Handles It                                                                 |\n|------------------------------------------|-----------------------------------------------------------------------------|------------------------------------------------------------------------------------------|\
| **Task handler crashes (uncaught exception)** | The handler raises an exception that is not caught. | The exception is caught by the worker, the task is marked `failed`, `attempt` is incremented, and the task is scheduled for retry with exponential backoff. After 5 failures, the task is left `failed` (human inspection). |\n| **Worker thread killed (SIGKILL, power loss)** | The worker process is terminated abruptly. | The task remains `running` but is considered stale after 5 minutes; the housekeeping thread resets it to `pending`. No task is ever permanently stuck. |\n| **Database corruption** | SQLite file becomes unreadable or inconsistent. | The library uses `PRAGMA journal_mode = WAL` and `PRAGMA synchronous = NORMAL` for durability. On startup, it runs `PRAGMA integrity_check` and repairs minor issues. If corruption is severe, the library logs a fatal error and exits, prompting the operator to restore from backup. |\n| **Disk full** | No space to write new rows. | The library checks `disk_full()` (via `sqlite3`'s `PRAGMA wal_checkpoint` and OS-level `df`) before enqueuing. If full, it returns an error to the caller and does not enqueue. The operator must free space. |\n| **Network latency (if handlers call external services)** | External API is slow or intermittent. | The exponential backoff ensures that retries do not hammer the external service. The worker does not retry indefinitely; after 5 failures, the task is left for human inspection. |\n| **Race condition: two callers enqueue the same logical job** | Two threads call `queue.enqueue` with the same `idempotency_key`. | The `enqueue` method checks for an existing row with the same `idempotency_key` in `pending` or `failed` state. If found, it returns the existing `task_id` and does not create a new row. Thus, duplicate work is prevented. |\n| **Task scheduled for the future, but the system clock is wrong** | `scheduled_at` is in the past due to a wrong system time. | The housekeeping thread uses `NOW()` from SQLite, which reflects the system clock. If the clock is wrong, all tasks will be treated as either immediately runnable or stale. The operator must ensure correct system time. |\n| **Handler takes longer than expected (e.g., 10 minutes)** | A legitimate long-running task. | The 5-minute stale threshold is chosen to be far shorter than any legitimate task duration. If a task genuinely takes longer, it will remain `running` for the full duration and will not be reset. The operator can adjust the threshold if needed. |\n| **SQLite lock contention under high concurrency** | Many workers try to claim tasks simultaneously. | The `SELECT ... FOR UPDATE` pattern ensures that only one worker can claim a task at a time. The queue's housekeeping thread also uses `FOR UPDATE` when resetting stale tasks, preventing deadlocks. |\n| **Memory pressure causing OOM killer** | The process is killed due to low memory. | Same as SIGKILL: any `running` tasks are reset after 5 minutes. The operator must ensure sufficient memory for the expected workload. |\n| **Human error: marking a task dead prematurely** | An operator calls `mark_dead` on a task that could still succeed. | The `mark_dead` method is explicit and requires a `task_id`. The operator is responsible for ensuring correctness. The design does not provide any automatic protection against this. |\n\n---\n\n## Trade-offs Rejected and Why\n\n| Trade-off Considered                     | Decision (Rejected) | Rationale                                                                 |\n|----------------------------------------|---------------------|--------------------------------------------------------------------------|\
