{"name": "write_file", "args": {"path": "DESIGN.md", "content": "# taskq Design Document\n\n## Overview\n\n**taskq** is a durable, in-process task queue built entirely in Python using SQLite. It provides a simple API for enqueuing named tasks with JSON payloads, running them via registered handler functions, and guaranteeing that no work is lost even if the host process crashes. It is deliberately scoped to a single machine with one SQLite file and one or more worker threads inside the same process.\n\nThe core guarantees are:\n- **Durability**: Tasks are persisted immediately upon enqueue; a crash mid-run never loses work.\n- **Atomic claiming**: A task can be executed by at most one worker at a time.\n- **Crash recovery**: If a worker is killed (SIGKILL, power loss), the task it was working on becomes runnable again.\n- **Backoff retries**: Failed tasks are retried with exponential backoff to avoid hammering failing dependencies.\n- **Duplicate prevention**: Racing callers cannot enqueue the same logical job twice.\n- **Observability**: Operators can query counts of pending, running, failed, and dead tasks.\n\nThe design below details each of these guarantees and the mechanisms used to achieve them.\n\n## Public API\n\nAll user-facing functions and classes are documented here. def enqueue(name: str, payload: Any, retry: int = 3, scheduled: Optional[float] = None) -> str
```\n\n**Arguments**\n- `name` (str): The task name. Must be registered via `taskq.register` before any tasks of this name are enqueued. The name is used as the key for deduplication (see *Duplicate prevention* below).\n- `payload` (Any): Must be JSON-serializable. Stored verbatim in the database.\n- `retry` (int, default 3): Maximum number of retry attempts after a failure. If a task fails `retry` times, it is marked `DEAD` and never retried.\n- `scheduled` (Optional[float], default None): Unix timestamp (seconds since epoch) at which the task should be considered runnable. If `None`, the task is immediately runnable. This enables delayed execution (e.g., \"run this in ten minutes\").\n\n**Returns**\n- A UUID string (`task_id`) that uniquely identifies the task. This ID is used for all subsequent queries about the task.\n\n**Behavior**\n1. Validate that `name` is registered (raise `taskq.UnregisteredTaskError` otherwise).\n2. Validate that `payload` is JSON-serializable (raise `taskq.InvalidPayloadError` otherwise).\n3. Insert a new row into the `tasks` table with columns `task_id`, `name`, `payload`, `retry_count`, `scheduled_at`, `status`. The `task_id` is generated as a UUIDv4 and inserted as the primary key.\n4. If `scheduled` is provided, the row is inserted with `status = PENDING` and `scheduled_at = scheduled`. If `scheduled` is `None`, the row is inserted with `status = PENDING` and `scheduled_at = NULL` (meaning immediately runnable).\n5. The insert is atomic; the task is durable immediately.\n\n### `taskq.register`\n\n**Signature**\n```python
def register(name: str, handler: Callable[[Any], None]) -> None
```\n\n**Arguments**\n- `name` (str): The task name to register.\n- `handler` (Callable[[Any], None]): A function that takes a single argument (the deserialized `payload`) and runs the task. The schema is defined by a `CREATE TABLE` statement executed once at package import. The schema is immutable; migrations are not supported (the library is designed for a single version).\n\n### Tables\n\n#### `tasks`\n\n| Column | Type | Constraints | Description |\n|--------|------|-------------|-------------|\n| `task_id` | TEXT | PRIMARY KEY | UUIDv4 string, unique identifier for the task. |\n| `name` | TEXT | NOT NULL | The task name (must be registered). |\n| `payload` | TEXT | NOT NULL | JSON-encoded payload. |\n| `retry_count` | INTEGER | NOT NULL DEFAULT 0 | Number of times the task has failed. |\n| `scheduled_at` | REAL | | Unix timestamp (seconds) when the task becomes runnable. AND status = 'pending' AND (scheduled_at IS NULL OR scheduled_at <= <now>);`\n   - This is the atomic claim (see *Atomic claiming* below).\n3. **Run**: Worker calls the handler with `json.loads(payload)`. The handler runs in the worker thread.\n4. **Success**: `UPDATE tasks SET status = 'pending', finished_at = <now> WHERE task_id = ?;` (task returns to pending queue for possible re-claim by another worker if the handler was not exclusive — but in our design, a task is never re-queued after success; it simply disappears from the queue. This matches the spec: a task that succeeds is done.)\n5. **Failure**: `UPDATE tasks SET status = 'failed', retry_count = retry_count + 1, finished_at = <now> WHERE task_id = ?;`\n   - If `retry_count < max_retry` (default 3), the task remains in the `failed` status and will be re-claimed later (see *Retries and backoff*). If `retry_count >= max_retry`, the task is marked `dead` (see *Dead tasks*). \n\n## Retries and Backoff\n\n### Maximum retries\n\nEach task has a `retry` parameter (default 3). This is the maximum number of times the task may be retried after a failure. When a task fails:\n- If `retry_count < retry`, the task is marked `failed` and will be re-claimed later.\n- If `retry_count >= retry`, the task is marked `dead` and never re-claimed.\n\n### Backoff strategy\n\nTo avoid hammering a failing dependency, we use **exponential backoff with jitter**.\n\nWhen a worker claims a task, it also records the `next_retry_at` column (new in the schema) as the Unix timestamp when the task may be re-claimed again. The value is computed as:\n\n```\nnext_retry_at = now + (2 ** retry_count) * 60 + random.uniform(0, 60)\n```\n\nExplanation:\n- Base interval doubles each retry: 1 min, 2 min, 4 min, 8 min, etc. (2^retry_count minutes).\n- A random jitter of up to 60 seconds is added to prevent thundering herd when many tasks fail simultaneously.\n- The `next_retry_at` value is stored in the `tasks` table (new column `next_retry_at`).\n\nWhen the queue worker scans for tasks to run, it filters on `status = 'failed'` and `next_retry_at <= now`. This ensures that a task is not re-claimed until the backoff period has elapsed.\n\n### Why exponential backoff?\n\n- **Linear backoff** would still cause many tasks to retry at the same time if they all fail at the same moment (e.g., a downstream service goes down for 5 minutes). Exponential backoff spreads the retries over a much longer window, reducing load on the failing service.\n- **Jitter** prevents all tasks from retrying at exactly the same moment (which would still cause a spike). The random component ensures a uniform distribution of retry times.\n- The maximum interval (for `retry_count = 3`) is 8 minutes plus jitter, which is reasonable for most workloads. If a task truly never succeeds, the operator can manually inspect it (see *Dead tasks*). \n\n## Crash Recovery\n\n### What can crash?\n\nThe library must survive a crash of the host process (e.g., SIGKILL, power loss, OS reboot). The crash can occur at any point:\n- While a task is being enqueued (unlikely, but possible).\n- While a worker thread is running a handler.\n- While the queue worker is scanning for tasks to claim.\n- While the database is being written (SQLite has its own journal, but we must not rely on it for our guarantees).\n\n### Claiming is atomic\n\nThe core of crash recovery is that **claiming a task is atomic**. When a worker wants to run a task, it executes:\n\n```sql\nUPDATE tasks\nSET status = 'running', started_at = <now>\nWHERE task_id = ?\n  AND status = 'pending'\n  AND (scheduled_at IS NULL OR scheduled_at <= <now>)\n  AND (next_retry_at IS NULL OR next_retry_at <= <now>);\n```\n\nBecause SQLite supports row-level locking and the `UPDATE` statement is atomic, only one worker can succeed in changing a task's status from `pending` to `running`. All other workers will see the updated status and skip that task. This guarantees that a task is never executed by two workers simultaneously.\n\n### What happens on crash?\n\nIf a crash occurs while a worker is executing a handler:\n- The worker may have already changed the task's status to `running` and recorded `started_at`.\n- The crash terminates the process; the SQLite connection is lost.\n- On restart, the queue worker scans for tasks with `status = 'running'` and `finished_at IS NULL`. These are exactly the tasks that were in progress at the time of crash.\n- The worker **reclaims** each such task: it updates the status back to `pending` (or `failed` if the handler had already failed) and clears `started_at` and `finished_at`. This makes the task runnable again.\n\nBecause the claim is atomic, there is no race condition where another worker could have already taken the same task. The only way a task could be lost is if the crash happened *before* the `UPDATE` that changed the status to `running`. In that case, the task remains `pending` and will be claimed by another worker on restart — which is exactly the desired behavior.\n\n### Summary of crash recovery steps\n\n1. On startup, the queue worker runs a `SELECT` for tasks with `status = 'running'` and `finished_at IS NULL`.\n2. For each such task, it executes an `UPDATE` that sets `status = 'pending'`, clears `started_at` and `finished_at`, and (if the task had a `next_retry_at`) ensures it is still eligible for re-claim (by not changing `next_retry_at`).\n3. The task is now in the pending queue and will be claimed by a worker on the next scan.\n\nThis design guarantees that no task is ever stuck in `running` forever after a crash.\n\n## Failure Modes and How They Are Handled\n\nBelow is a non-exhaustive list of failure modes we considered, how they manifest, and how the design mitigates them.\n\n| Failure mode | How it manifests | Mitigation |\n|--------------|------------------|------------|\n| **Process killed mid-handler** | Worker thread receives SIGKILL or power loss while executing a handler. | The task's status is already `running`. On restart, the queue worker reclaims it (see *Crash recovery*). No task is lost. |\n| **Database corruption** | SQLite file becomes unreadable (e.g., disk failure). | SQLite has its own journal and WAL modes; we use `PRAGMA journal_mode = WAL` and `PRAGMA synchronous = NORMAL` to maximize durability. If corruption occurs, the application will crash and the operator must restore from backup. This is an external failure mode beyond the library's control. |\n| **Race between enqueue and register** | A caller enqueues a task for a name that hasn't been registered yet. | `enqueue` checks the `handlers` table; if the name is missing, it raises `taskq.UnregisteredTaskError`.
