```### Overview of the Approach

The `taskq` library will be a durable in-process task queue implemented in Python using the standard library, specifically the `sqlite3` module for persistence. The library will allow a single application to enqueue background work and process it reliably, ensuring that tasks survive a crash of the host process. The design will support multiple worker threads within the same process, ensuring thread safety and preventing duplicate work. Tasks will be claimed atomically with an expiration mechanism to handle worker failures gracefully. Retries will include exponential backoff to avoid hammering failing dependencies. 1. **Tasks Table:**
   ```sql
   CREATE TABLE tasks (
       id INTEGER PRIMARY KEY AUTOINCREMENT,
       task_name TEXT NOT NULL,
       payload TEXT NOT NULL,
       status TEXT NOT NULL DEFAULT 'pending',
       scheduled_at INTEGER NOT NULL DEFAULT CURRENT_TIMESTAMP,
       claimed_by TEXT,
       claim_expires_at INTEGER,
       retry_count INTEGER NOT NULL DEFAULT 0,

   );

   CREATE TABLE handlers (

```### Retries and Backoff

The `taskq` library will implement an exponential backoff strategy for retries. When a task fails, it will be retried after an increasing delay. The delay will be calculated using the formula:

\[ \text{delay} = \min(\text{base\_delay} \times 2^{\text{retry\_count}}, \text{max\_delay}) \]

Where:
- `base_delay` is the initial delay in seconds (e.g., 1 second).
- `max_delay` is the maximum delay in seconds (e.g., 60 seconds).
- `retry_count` is the number of times the task has been retried.

For example, if a task fails on its first attempt, it will be retried after 1 second. If it fails again, it will be retried after 2 seconds, then 4 seconds, and so on, up to a maximum of 60 seconds.

```### Crash Recovery

The `taskq` library will ensure that tasks are not lost if the process is killed mid-run. This will be achieved through the following mechanisms:

1. **Atomic Task Claiming:**
   When a worker claims a task, it will update the `claimed_by` and `claim_expires_at` fields in the `tasks` table atomically. The `claim_expires_at` field will be set to a future timestamp, ensuring that the task can be reclaimed if the worker does not complete it within the expected time.

2. **Task Reclamation:**
   If a worker is killed, the task will be automatically reclaimed by another worker when its claim expires. This is ensured by periodically checking for tasks with expired claims and reassigning them to available workers.

3. **Persistent Task State:**
   All task states, including their status, retry count, and last attempted time, will be stored in the SQLite database. This ensures that the state is preserved across process restarts.

By implementing these mechanisms, the `taskq` library will be able to recover from crashes and ensure that tasks are processed reliably.
