FOR UPDATE` lock on the `tasks` table, then updating the `status` to `running`. This guarantees that no two workers can ever claim the same task, and that a crashed worker will release the lock immediately (SQLite releases locks when the connection closes).\n- **No duplicate work via idempotent task IDs**: Each logical job is given a unique `task_id` (UUID v4). This is the maximum number of **attempts** (including the first attempt). If a task fails `retries` times, it is marked `failed` and never retried again.\n- The limit is enforced by the worker loop: after each exception, the worker checks `if attempt >= task.retries: mark as failed; else backoff and retry`.\n\n### Backoff algorithm\n\nWe use **exponential backoff with jitter** to avoid hammering a failing downstream service.\n\n- **Base backoff**: 1 second.\n- **Multiplier**: 2 (doubling each attempt).\n- **Jitter**: Uniform random offset in `[-0.1s, +0.1s]` (100 ms) to spread out retries across workers.\n\n**Formula** (for attempt `i`, 0‑indexed):\n```\nbackoff_i = (2^i) * 1s + Uniform(-0.1s, +0.1s)\n```\n\n**Sequence** (for a task with `retries = 5`):\n- Attempt 0 (first run): 1s ± 0.1s\n- Attempt 1: 2s ± 0.1s\n- Attempt 2: 4s ± 0.1s\n- Attempt 3: 8s ± 0.1s\n- Attempt 4: 16s ± 0.1s\n- After attempt 4 fails → task is marked `failed` (no further retries).\n\n### Why this design?\n\n- **Exponential growth** ensures that a failing service is not hammered with rapid retries, giving it time to recover.\n- **Jitter** prevents all workers from retrying at exactly the same moment (which would cause a thundering‑herd storm).\n- **Fixed maximum** (5) keeps the total retry window bounded (≈ 31 seconds worst case), which is reasonable for most background jobs.\n- **No configurable backoff factor** in the public API: we chose a simple, well‑understood algorithm and exposed only the retry count, which is the most important knob for users.\n\n---\n\n## Crash Recovery\n\n### What can crash?\n\n- The entire process (SIGKILL, power loss, OS kill).\n- A worker thread (e.g., `threading.Thread` dies unexpectedly).\n- The database connection (e.g., `sqlite3` connection is closed abruptly).\n\n### How we guarantee recovery\n\n1. **Atomic claiming via `SELECT ... FOR UPDATE`**\n   - When a worker wants to claim a task, it executes:\n     ```sql\n     SELECT task_id, name, payload, retries, scheduled_at, claimed_at, started_at, finished_at, error\n     FROM tasks
     WHERE status = 'pending'
       AND (scheduled_at IS NULL OR scheduled_at <= datetime('now'))
     ORDER BY scheduled_at, task_id
     LIMIT 1
     FOR UPDATE;
     ```
   - This statement acquires a row‑level lock on the selected task, guaranteeing that no other worker can claim the same task concurrently.
   - If the process crashes **before** the `UPDATE tasks SET status = 'running' ...` is executed, the `SELECT ... FOR UPDATE` lock is automatically released by SQLite when the connection closes. The task remains `pending` and will be re‑selected by the next worker.\n\n2. **Status as the single source of truth**\n   - A task is `pending` until a worker updates it to `running`. If a worker crashes after updating to `running` but before finishing, the task will stay `running` until the next worker claims it (see below).\n   - However, SQLite **does not** hold a lock on a row after the `UPDATE` completes; the lock is released immediately. If the process crashes after the `UPDATE`, the task will remain `running` and will never be re‑claimed. To avoid this, we add a **claim timeout** (see below).\n\n3. **Claim timeout (TTL)**\n   - After a worker updates `status = 'running'`, it also records `claimed_at = datetime('now')`.\n   - Workers periodically (every 30 seconds) run a cleanup query:\n     ```sql\n     UPDATE tasks
     SET status = 'pending', claimed_at = NULL, started_at = NULL, finished_at = NULL, error = NULL
     WHERE status = 'running'
       AND (julianday('now') - julianday(claimed_at)) > 30;
     ```
   - This ensures that any task stuck in `running` for more than 30 seconds (likely due to a crashed worker) is automatically reset to `pending`, making it available again.\n   - The 30‑second window is a trade‑off: long enough to allow a slow worker to finish, short enough to prevent indefinite hangs.\n\n4. **No orphaned `running` tasks after a full process crash**\n   - If the entire process dies, SQLite releases all locks, and the `stats` counters are left as‑is. On restart, the application calls `get_stats()` and sees the stale `running` count. However, the next worker will immediately run the cleanup query (see above) and reset any `running` tasks that exceed the TTL, so the queue will self‑heal.\n   - For tasks that were `running` but not yet claimed (i.e., the `SELECT ... FOR UPDATE` succeeded but the `UPDATE` failed), the `SELECT` lock is released, and the task remains `pending`. No recovery is needed.\n\n### Summary of crash recovery guarantees\n\n- **No task can be claimed by two workers simultaneously** (row‑level lock).\n- **A crashed worker never leaves a task permanently stuck** (TTL cleanup resets `running` tasks after 30 seconds).\n- **All state is persisted in SQLite**, so a restart will see the correct `status` for each task.\n- **Operators can always query `get_stats()`** to see the current state, even after a crash.\n\n---\n\n## Failure Modes and How the Design Handles Them\n\n| Failure mode | What happens | How the design handles it |\n|--------------|--------------|---------------------------|\

This is the maximum number of **attempts** (including the first attempt). If a task fails `retries` times, it is marked `failed` and never retried again.\n- The limit is enforced by the worker loop: after each exception, the worker checks `if attempt >= task.retries: mark as failed; else backoff and retry`.\n\n### Backoff algorithm\n\nWe use **exponential backoff with jitter** to avoid hammering a failing downstream service.\n\n- **Base backoff**: 1 second.\n- **Multiplier**: 2 (doubling each attempt).\n- **Jitter**: Uniform random offset in `[-0.1s, +0.1s]` (100 ms) to spread out retries across workers.\n\n**Formula** (for attempt `i`, 0‑indexed):\n```\nbackoff_i = (2^i) * 1s + Uniform(-0.1s, +0.1s)\n```\n\n**Sequence** (for a task with `retries = 5`):\n- Attempt 0 (first run): 1s ± 0.1s\n- Attempt 1: 2s ± 0.1s\n- Attempt 2: 4s ± 0.1s\n- Attempt 3: 8s ± 0.1s\n- Attempt 4: 16s ± 0.1s\n- After attempt 4 fails → task is marked `failed` (no further retries).\n\n### Why this design?\n\n- **Exponential growth** ensures that a failing service is not hammered with rapid retries, giving it time to recover.\n- **Jitter** prevents all workers from retrying at exactly the same moment (which would cause a thundering‑herd storm).\n- **Fixed maximum** (5) keeps the total retry window bounded (≈ 31 seconds worst case), which is reasonable for most background jobs.\n- **No configurable backoff factor** in the public API: we chose a simple, well‑understood algorithm and exposed only the retry count, which is the most important knob for users.\n\n---\n\n## Crash Recovery\n\n### What can crash?\n\n- The entire process (SIGKILL, power loss, OS kill).\n- A worker thread (e.g., `threading.Thread` dies unexpectedly).\n- The database connection (e.g., `sqlite3` connection is closed abruptly).\n\n### How we guarantee recovery\n\n1. **Atomic claiming via `SELECT ... FOR UPDATE`**\n   - When a worker wants to claim a task, it executes:\n     ```sql\n     SELECT task_id, name, payload, retries, scheduled_at, claimed_at, started_at, finished_at, error\n     FROM tasks\n     WHERE status = 'pending'\n       AND (scheduled_at IS NULL OR scheduled_at <= datetime('now'))\n     ORDER BY scheduled_at, task_id\n     LIMIT 1\n     FOR UPDATE;\n     ```\n   - This statement acquires a row‑level lock on the selected task, guaranteeing that no other worker can claim the same task concurrently.\n   - If the process crashes **before** the `UPDATE tasks SET status = 'running' ...` is executed, the `SELECT ... The task remains `pending` and will be re‑selected by the next worker.\n\n2. **Status as the single source of truth**\n   - A task is `pending` until a worker updates it to `running`. If a worker crashes after updating to `running` but before finishing, the task will stay `running` until the next worker claims it (see below).\n   - However, SQLite **does not** hold a lock on a row after the `UPDATE` completes; the lock is released immediately. If the process crashes after the `UPDATE`, the task will remain `running` and will never be re‑claimed. To avoid this, we add a **claim timeout** (see below).\n\n3. **Claim timeout (TTL)**\n   - After a worker updates `status = 'running'`, it also records `claimed_at = datetime('now')`.\n   - Workers periodically (every 30 seconds) run a cleanup query:\n     ```sql\n     UPDATE tasks\n     SET status = 'pending', claimed_at = NULL, started_at = NULL, finished_at = NULL, error = NULL\n     WHERE status = 'running'\n       AND (julianday('now') - julianday(claimed_at)) > 30;\n     ```\n   - This ensures that any task stuck in `running` for more than 30 seconds (likely due to a crashed worker) is automatically reset to `pending`, making it available again.\n   - The 30‑second window is a trade‑off: long enough to allow a slow worker to finish, short enough to prevent indefinite hangs.\n\n4. **No orphaned `running` tasks after a full process crash**\n   - If the entire process dies, SQLite releases all locks, and the `stats` counters are left as‑is. On restart, the application calls `get_stats()` and sees the stale `running` count. FOR UPDATE` succeeded but the `UPDATE` failed), the `SELECT` lock is released, and the task remains `pending`. No recovery is needed.\n\n### Summary of crash recovery guarantees\n\n- **No task can be claimed by two workers simultaneously** (row‑level lock).\n- **A crashed worker never leaves a task permanently stuck** (TTL cleanup resets `running` tasks after 30 seconds).\n- **All state is persisted in SQLite**, so a restart will see the correct `status` for each task.\n- **Operators can always query `get_stats()`** to see the current state, even after a crash.\n\n---\n\n## Failure Modes and How the Design Handles Them\n\n| Failure mode | What happens | How the design handles it |\n|--------------|--------------|---------------------------|\n| **Task handler raises a transient exception** (e.g., network timeout) | The worker catches the exception, logs it, and schedules a retry after backoff. | The `retries` counter limits attempts; exponential backoff prevents hammering.
