It provides a simple API for enqueueing background work, with automatic retry logic, idempotency guarantees, and a clear separation between transient and permanent failures. The design prioritizes correctness over performance, assuming modest throughput (hundreds of tasks/sec) and a single machine with one or more worker threads.\n\nCore design principles:\n- **Durability**: No task is ever lost, even if the process is killed mid-run.\n- **Atomicity**: Task claiming, scheduling, and execution are atomic operations to prevent race conditions.\n- **Idempotency**: Duplicate enqueues of the same logical job are automatically deduplicated.\n- **Fail-fast with recovery**: Failed tasks are retried with exponential backoff, then moved to a dead queue for human inspection.\n- **Simple persistence**: All state lives in a single SQLite database, making recovery trivial.\n\n## Public API\n\n### `taskq.init(db_path: str, max_retries: int = 3, retry_base: float = 1.0, retry_max: float = 60.0, idempotency_key_prefix: str = \"taskq:\")` → `None`\n\nInitializes the task queue, creating the database schema if it doesn't exist. marked as `failed` and its `failure_count` is incremented.\n- If `failure_count < max_retries`, the task is immediately re-enqueued as `pending`.\n- If `failure_count >= max_retries`, the task is moved to the `dead` state and copied to the `dead_tasks` table.\n\n### Exponential Backoff\n- Delay between retries follows exponential backoff: `delay = min(retry_base * (2 ** (failure_count - 1)), retry_max)`.\n- Default parameters: `retry_base = 1.0` seconds, `retry_max = 60.0` seconds.\n- This ensures that repeated failures do not hammer a failing dependency.\n\n### Claim Expiration\n- When a worker claims a task, it sets `claimed_at` and `expires_at = claimed_at + 30 seconds`.\n- If a worker crashes before completing the task, the claim expires after 30 seconds, and the task becomes available again.\n- This prevents tasks from being stuck forever due to a crashed worker.\n\n## Crash Recovery\n\n### On Process Restart\n- The `init()` function checks if the database exists. If not, it creates the schema.\n- All tasks are re-read from the `tasks` table, regardless of their `status`.\n- Tasks in `failed` or `dead` states are left as-is (they will be retried or inspected by humans).\n- Tasks in `pending` or `running` states are re-evaluated:\n  - If `expires_at` is in the past, the task is re-queued as `pending`.\n  - If `expires_at` is in the future, the task remains `running` (the worker will re-claim it when it restarts).\n\n### On Worker Crash (SIGKILL, power loss)\n- The worker's `pid` is removed from the `workers` table.\n- Any `running` tasks claimed by that worker are re-evaluated:\n  - If `expires_at` is in the past, the task is re-queued as `pending`.\n  - If `expires_at` is in the future, the task remains `running` (the worker will re-claim it when it restarts).\n\n### On Database Corruption\n- SQLite has built-in journaling and WAL (Write-Ahead Logging) modes to minimize corruption risk.\n- `init()` opens the database in `SQLITE_OPEN_READWRITE | SQLITE_OPEN_CREATE` mode, which will fail if the database is corrupted, prompting a manual recovery.\n- For robustness, `init()` can be extended to attempt a `PRAGMA integrity_check` and rebuild the schema if needed (out of scope for this design).\n\n## Failure Modes and Handling\n\n| Failure Mode                     | Handling                                                                                                   |\n|----------------------------------|-----------------------------------------------------------------------------------------------------------|\
| Task handler raises exception    | Caught, `failure_count` incremented, task re-queued with backoff (unless `max_retries` exceeded).         |\
| Worker crashes mid-task          | Claim expires after 30 seconds; task becomes `pending` again.                                            |\
| Database corruption              | `init()` fails; manual recovery required (e.g., restore from backup, rebuild schema).                  |\
| Disk full / I/O error           | SQLite will raise an exception; task is left in `failed` state for human inspection.                  |\
| Duplicate enqueue of same job    | Idempotency key prevents duplicate execution; only one task is processed.                               |\
| Race between enqueue and claim   | Claim is atomic (SELECT ... FOR UPDATE); only one worker can claim a task at a time.                  |\
| Handler takes too long           | Task remains `running` until `expires_at` passes; no timeout beyond claim expiration.                  |\
| Memory exhaustion               | Not handled explicitly; relies on OS to kill the process, triggering crash recovery.                  |\
\n## Trade-offs Rejected and Why\n\n### 1. Distributed Coordination (e.g., Redis, ZooKeeper)\n**Rejected.** The spec explicitly states this is a single-machine, in-process solution. Distributed coordination would add complexity, require external dependencies, and violate the \"no cross-machine coordination\" constraint.\n\n### 2. Priority Queues or Weighted Scheduling\n**Rejected.** The spec does not mention priority classes, and adding them would complicate the schema and retry logic unnecessarily. All tasks are treated equally; urgency is expressed via `scheduled_at`.\n\n### 3. Task Cancellation\n**Rejected.** The spec says cancellation is out of scope. Implementing cancellation would require additional state (e.g., `cancelled_at`) and race conditions between cancellation and execution, which we want to avoid.\n\n### 4. Cron-like Scheduled Expressions\n**Rejected.** The spec limits scheduling to a simple `scheduled_at` Unix timestamp. Cron expressions would require parsing and evaluation logic, increasing complexity and potential for bugs.\n\n### 5. Web UI for Monitoring\n**Rejected.** The spec explicitly excludes a web UI. Observability is provided via `get_stats()` and `dead_tasks()`, which can be called from any tool or script.\n\n### 6. In-memory-only storage (e.g., `dict`)\n**Rejected.** Without persistence, a crash would lose all tasks. The spec requires durability, so SQLite is the only viable option given the constraints.\n\n### 7. Asyncio-based workers\n**Rejected.** The spec allows multiple worker threads, but not async workers. Using `asyncio` would require a different event loop and could complicate the claim/release semantics. Threads are simpler and sufficient for the modest throughput target.\n\n### 8. Per-task file-based storage\n**Rejected.** Storing each task as a separate file would complicate recovery (many small files) and make the schema less uniform. SQLite provides a single, atomic, and reliable storage mechanism.\n\n### 9. Optimistic concurrency (e.g., `SELECT ... WHERE status='pending'` without `FOR UPDATE`)\n**Rejected.** This would allow two workers to claim the same task simultaneously, violating the \"no task may be executed by two workers at once\" requirement. We use `SELECT ... FOR UPDATE` to ensure atomic claiming.\n\n### 10. Automatic retry without backoff (linear retries)\n**Rejected.** Linear retries would hammer a failing dependency. Exponential backoff is a standard, well-understood approach that balances retry frequency with resource usage.\n\n### 11. No idempotency (allow duplicate execution)\n**Rejected.** The spec explicitly requires \"no duplicate work when the same logical job is enqueued twice by racing callers.\" Idempotency keys provide a simple, deterministic way to enforce this.\n\n### 12. No dead queue (just delete failed tasks)\n**Rejected.** Deleting failed tasks would lose information needed for debugging and human inspection. The dead queue preserves all failed tasks for later analysis.\n\n### 13. No worker tracking (no `workers` table)\n**Rejected.** While not strictly required for correctness, tracking workers helps with debugging and recovery (e.g., knowing which PID claimed a task). It's a small overhead for significant benefit.\n\n### 14. No `get_stats()` (rely on raw SQL)\n**Rejected.** The spec requires observability: \"an operator must be able to ask how many tasks are pending, running, failed, and dead.\" `get_stats()` provides a clean, thread-safe way to retrieve this information without exposing raw SQL.\n\n### 15. No `dead_tasks()` (just rely on `get_stats()`)\n**Rejected.** `get_stats()` only gives counts; `dead_tasks()` returns the actual task data, which is essential for human inspection and debugging.\n\n### 16. started.                                   |\n\n**Indexes:** `pid`\n\n## Retry and Backoff Strategy\n\n### Retry Policy\n- Each task has a `max_retries` limit (default 3).\n- On failure, the task is marked as `failed` and its `failure_count` is incremented.\n- If `failure_count < max_retries`, the task is immediately re-enqueued as `pending`.\n- If `failure_count >= max_retries`, the task is moved to the `dead` state and copied to the `dead_tasks` table.\n\n### Exponential Backoff\n- Delay between retries follows exponential backoff: `delay = min(retry_base * (2 ** (failure_count - 1)), retry_max)`.\n- Default parameters: `retry_base = 1.0` seconds, `retry_max = 60.0` seconds.\n- This ensures that repeated failures do not hammer a failing dependency.\n\n### Claim Expiration\n- When a worker claims a task, it sets `claimed_at` and `expires_at = claimed_at + 30 seconds`.\n- If a worker crashes before completing the task, the claim expires after 30 seconds, and the task becomes available again.\n- This prevents tasks from being stuck forever due to a crashed worker.\n\n## Crash Recovery\n\n### On Process Restart\n- The `init()` function checks if the database exists. If not, it creates the schema.\n- All tasks are re-read from the `tasks` table, regardless of their `status`.\n- Tasks in `failed` or `dead` states are left as-is (they will be retried or inspected by humans).\n- Tasks in `pending` or `running` states are re-evaluated:\n  - If `expires_at` is in the past, the task is re-queued as `pending`.\n  - If `expires_at` is in the future, the task remains `running` (the worker will re-claim it when it restarts).\n\n### On Worker Crash (SIGKILL, power loss)\n- The worker's `pid` is removed from the `workers` table.\n- Any `running` tasks claimed by that worker are re-evaluated:\n  - If `expires_at` is in the past, the task is re-queued as `pending`.\n  - If `expires_at` is in the future, the task remains `running` (the worker will re-claim it when it restarts).\n\n### On Database Corruption\n- SQLite has built-in journaling and WAL (Write-Ahead Logging) modes to minimize corruption risk.\n- `init()` opens the database in `SQLITE_OPEN_READWRITE | SQLITE_OPEN_CREATE` mode, which will fail if the database is corrupted, prompting a manual recovery.\n- For robustness, `init()` can be extended to attempt a `PRAGMA integrity_check` and rebuild the schema if needed (out of scope for this design).\n\n## Failure Modes and Handling\n\n| Failure Mode                     | Handling                                                                                                   |\n|----------------------------------|-----------------------------------------------------------------------------------------------------------|\n| Task handler raises exception    | Caught, `failure_count` incremented, task re-queued with backoff (unless `max_retries` exceeded).         |\n| Worker crashes mid-task          | Claim expires after 30 seconds; Distributed Coordination (e.g., Redis, ZooKeeper)\n**Rejected.** The spec explicitly states this is a single-machine, in-process solution. Priority Queues or Weighted Scheduling\n**Rejected.** The spec does not mention priority classes, and adding them would complicate the schema and retry logic unnecessarily. All tasks are treated equally; urgency is expressed via `scheduled_at`.\n\n### 3. Task Cancellation\n**Rejected.** The spec says cancellation is out of scope. Implementing cancellation would require additional state (e.g., `cancelled_at`) and race conditions between cancellation and execution, which we want to avoid.\n\n### 4. Cron-like Scheduled Expressions\n**Rejected.** The spec limits scheduling to a simple `scheduled_at` Unix timestamp. Per-task file-based storage\n**Rejected.** Storing each task as a separate file would complicate recovery (many small files) and make the schema less uniform.
