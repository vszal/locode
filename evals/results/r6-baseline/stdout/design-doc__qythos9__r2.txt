The flow is:\n\n1. A worker claims a task via `claim(lock_id)`. If successful, it receives `(task_id, payload)` and runs the registered handler.\n2. The handler may raise an exception (or return `False` via `taskq.complete(task_id, success=False)`). In either case, the worker calls `taskq.complete(task_id, success=False)`.\n3. `taskq.complete` checks the `retry_policy` for the task name (if any). If the `attempt` is less than `max_attempts`, it updates the `tasks` row: `attempt = attempt + 1`, `state = 'pending'`, `last_attempt_at = now()`, and `scheduled_at = now() + backoff_base * (2 ** attempt)` (exponential backoff). The `task_locks` row is deleted, and the task will never be re-queued.\n\n**Backoff formula:** `backoff = backoff_base * (2 ** attempt)`. For example, with `backoff_base=1.0` and `max_attempts=5`, the backoffs are 1s, 2s, 4s, 8s, 16s. This ensures that a failing dependency is not hammered, and the backoff grows exponentially, which is a common pattern for transient failures.\n\n**Policy customization:** Users can provide a `retry_policy` dict in `taskq.init`. The `task_locks` row remains, but the `tasks` row may be in `running` state (or `failed` if the handler raised). When the process restarts, `taskq` runs a recovery routine (called automatically by `taskq.init` if the database already exists, or by `taskq.run_worker` on first start) that does the following:\n\n1. Scan `task_locks` for rows where `lock_id` does not exist in `tasks` (i.e., the task was never created, or the `tasks` row was deleted due to a bug). These rows are deleted (they are stale).\n2. For rows where `lock_id` exists in `tasks`, check the `state` of the `tasks` row:\n   - If `state` is `running`, `failed`, `dead`, or `done`, the task is in a terminal state. The `task_locks` row is deleted (it is no longer needed).\n   - If `state` is `pending`, the task is still runnable. However, the `task_locks` row may be stale (e.g., the worker crashed before completing the task). In this case, we **re-insert** the `task_locks` row with a fresh `claimed_at` timestamp, effectively re-claiming the task for a new worker. This ensures that the task will be processed again.\n3. For rows where `lock_id` does not exist in `tasks` but `state` is `pending`, we **re-insert** the `tasks` row (with `state='pending'`, `attempt=0`, `scheduled_at=now()`) and delete the stale `task_locks` row. This is the core guarantee: a killed worker will never leave a task stuck forever.\n\n**Why this works:** The `UNIQUE(lock_id)` constraint ensures that a `lock_id` can only be claimed once. If a worker crashes, the `lock_id` remains in `task_locks`, but the `tasks` row is still `pending`. The recovery routine will see that `lock_id` exists in `task_locks` but `state` is `pending`, so it will re-insert the `task_locks` row (with a fresh `claimed_at`). This effectively re-claims the task for a new worker, and the `tasks` row remains `pending`, so it will be processed again.\n\n**Edge case:** If a task is in `failed` state (i.e., `attempt >= max_attempts`), the recovery routine will delete the `task_locks` row (since the task is terminal). This ensures that the task will never be re-queued.\n\n## Failure Modes and Handling\n\nWe considered several failure modes and designed the system to handle each as follows:\n\n| Failure mode | How it manifests | How the design handles it |\n|--------------|------------------|---------------------------|\
