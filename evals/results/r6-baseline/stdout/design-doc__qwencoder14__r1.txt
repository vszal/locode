The `taskq` library will be a durable in-process task queue implemented in Python using the standard library, specifically the `sqlite3` module for persistence. The library will allow a single application to enqueue background work and process it reliably, ensuring that tasks are not lost if the process is killed mid-run and that no task is executed by two workers at once. The design will support multiple worker threads within the same process and will handle task retries with exponential backoff, ensuring that failing dependencies are not hammered. ```### Public API

The `taskq` library will expose the following public API:

1. **Enqueue Task:**
   - **Function:** `enqueue(name: str, payload: dict, delay: int = 0) -> None`
   - **Description:** Enqueues a named task with a JSON-serializable payload. If `delay` is specified, the task will be executed after the specified delay in seconds.
   - **Parameters:**
     - `name` (str): The name of the task handler.
     - `payload` (dict): The JSON-serializable payload for the task.
     - `delay` (int, optional): The delay in seconds before the task is executed. Defaults to 0.

2. **Register Task Handler:**
   - **Function:** `register_handler(name: str, handler: Callable[[dict], None]) -> None`
   - **Description:** Registers a handler function for a named task.
   - **Parameters:**
     - `name` (str): The name of the task handler.
     - `handler` (Callable[[dict], None]): The handler function that takes a dictionary payload and returns `None`.

3. **Start Workers:**
   - **Function:** `start_workers(num_workers: int) -> None`
   - **Description:** Starts a specified number of worker threads to process tasks.
   - **Parameters:**
     - `num_workers` (int): The number of worker threads to start.

4. **Get Task Status:**
   - **Function:** `get_status() -> dict`
   - **Description:** Returns the current status of the task queue, including the number of pending, running, failed, and dead tasks.
   - **Returns:** A dictionary with the following keys:
     - `pending` (int): Number of tasks waiting to be processed.
     - `running` (int): Number of tasks currently being processed.
     - `failed` (int): Number of tasks that have failed.
     - `dead` (int): Number of tasks that have been set aside for human inspection.

5. **Signal Task Completion:**
   - **Function:** `signal_completion(task_id: str, success: bool) -> None`
   - **Description:** Signals the completion of a task, indicating whether it succeeded or failed.
   - **Parameters:**
     - `task_id` (str): The unique identifier of the task.
     - `success` (bool): `True` if the task succeeded, `False` if it failed.

These functions provide a comprehensive interface for enqueuing tasks, registering handlers, managing workers, and monitoring the status of the task queue.```tool

```### Retries and Backoff

The `taskq` library will implement an exponential backoff strategy for retrying failed tasks. When a task fails, it will be retried after an increasing delay. The delay will be calculated using the formula:

\[ \text{delay} = \min(\text{base\_delay} \times 2^{\text{retry\_count}}, \text{max\_delay}) \]

Where:
- `base_delay` is the initial delay in seconds (e.g., 1 second).
- `retry_count` is the number of times the task has been retried.
- `max_delay` is the maximum delay in seconds (e.g., 60 seconds).

This strategy ensures that tasks are retried with increasing intervals, reducing the load on the system and giving failing dependencies time to recover. If a task fails a specified number of times (e.g., 5), it will be marked as dead and set aside for human inspection.```tool

```### Crash Recovery

The `taskq` library will ensure robust crash recovery by leveraging the durability of the SQLite database. When a task is claimed by a worker, it will be marked as running in the database. If the worker process is killed (e.g., via SIGKILL or power loss), the task will remain in the running state. Upon restart, the library will:

1. **Identify Stuck Tasks:** Query the database for tasks that are marked as running but have not been updated for a significant period (e.g., longer than the expected worker processing time).
2. **Reclaim Stuck Tasks:** Mark these tasks as pending, making them available for retry by other workers.
3. **Resume Processing:** Continue processing tasks as usual.

This approach ensures that no task is lost and that tasks that were in progress when a crash occurred are retried by other available workers.
