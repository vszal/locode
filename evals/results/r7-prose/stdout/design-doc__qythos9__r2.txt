After `max_retries` failures the task is marked `dead` and set aside for human inspection.\n- **Crash recovery** is automatic: on restart, workers scan for `running` tasks (which may have been left in that state by a killed worker) and re-claim them. FOR UPDATE`, a killed worker cannot leave a task permanently stuck.\n\n**What “no duplicate work” means:**\n- Each logical job is identified by a unique `task_id` (UUID) generated at enqueue time. The schema is defined as follows:\n\n```sql
CREATE TABLE IF NOT EXISTS tasks (\n    task_id TEXT PRIMARY KEY,\n    name TEXT NOT NULL,\n    payload TEXT NOT NULL,\n    scheduled_at DATETIME,\n    max_retries INTEGER NOT NULL,\n    backoff_ms INTEGER NOT NULL,\n    status TEXT NOT NULL DEFAULT 'pending',\n    retry_count INTEGER NOT NULL DEFAULT 0,\n    last_error TEXT,\n    claimed_at DATETIME,\n    completed_at DATETIME,\n    failed_at DATETIME,\n    dead_at DATETIME\n);\n\nCREATE INDEX IF NOT EXISTS idx_tasks_status ON tasks(status);\nCREATE INDEX IF NOT EXISTS idx_tasks_scheduled_at ON tasks(scheduled_at);\n```\n\n**Field descriptions:**\n- `task_id`: UUID (generated by `taskq.enqueue`). FOR UPDATE` on the `tasks` table, filtering for `status = 'pending'` and `scheduled_at <= now`. This ensures that only one worker can ever claim a given `task_id`.\n- The `task_id` is unique, so there is no possibility of two workers claiming the same task.\n\n**Crash recovery:**\n- If a worker is killed while a task is `running`, the `task_id` remains `running` and `claimed_at` is set. On restart, `taskq.pull` will see the `running` task (since `status` is still `running`) and will re-claim it (by updating `status` back to `pending` and resetting `claimed_at`). This ensures that no task is permanently stuck.\n- The `taskq.dead` state is permanent: once a task is `dead`, it will never be pulled again, and `taskq.count_tasks('dead')` will reflect it.\n\n**Data integrity:**\n- All writes are done via `taskq.enqueue`, `taskq.pull`, `taskq.complete`, `taskq.fail`, `taskq.dead`, `taskq.count_tasks`, `taskq.get_task`, `taskq.register_task_id`, `taskq.unregister_task_id`, `taskq.get_task_ids`. If future changes are required, a `schema_version` column could be added, but it is not part of the current design.\n\n---\n\n## Retries and Backoff\n\n**Retry policy:**\n- Each task has a `max_retries` (default 3) and a `backoff_ms` (default 1000 ms).\n- When a handler raises `taskq.RetryableError`, `taskq.fail(task_id, str(e))` is called, which increments `retry_count` and updates `status` to `'failed'` (if `retry_count < max_retries`).\n- If `retry_count == max_retries`, `taskq.dead(task_id)` is called, which sets `status` to `'dead'` and `dead_at` to now.\n- The task will never be retried again once it is `dead`.\n\n**Backoff algorithm:**\n- The backoff is exponential with jitter: for attempt `i` (1-indexed), the delay is `backoff_ms * (2 ** (i - 1)) * (0.5 + random(0, 0.5))`.\n- This ensures that repeated failures do not hammer a failing downstream service (e.g., a rate-limited API) and that the system is robust to transient spikes in load.\n- The jitter factor `0.5 + random(0, 0.5)` ensures that the delay is between `0.5 * backoff_ms * (2 ** (i - 1))` and `1.0 * backoff_ms * (2 ** (i - 1))`.\n\n**Implementation in `taskq.pull` loop:**\n- `taskq.pull` is called in a loop (e.g., `while True: task = taskq.pull(); we could have made it a float, but that would complicate the SQL schema and the `taskq.fail` logic. The integer is sufficient for the modest throughput target (hundreds of tasks per second).\n- The `max_retries` is a simple integer; we could have made it configurable per task, but that would add complexity to the schema and the `taskq.enqueue` API. The default `max_retries = 3` is a reasonable starting point.\n\n**What we rejected:**\n- **Dynamic backoff based on task type:** We considered allowing different backoff strategies for different task types (e.g., `send_email` vs. `process_image`). However, this would require a `backoff_strategy` column in the `tasks` table and a more complex `taskq.fail` implementation. Given the modest throughput target and the fact that most tasks will be simple (e.g., `send_email`, `process_image`), we decided to keep a single `backoff_ms` for all tasks. If a user needs a custom backoff, they can register a custom handler that raises `taskq.RetryableError` with a custom message, and the `taskq.fail` logic will still use the `backoff_ms` from the task metadata.\n- **Retry limit per task type:** We considered allowing a `max_retries_per_type` column, but this would complicate the schema and the `taskq.fail` logic. The `max_retries` per task is sufficient for most use cases.\n- **Retry limit per task name:** We considered allowing a `max_retries_per_name` column, but this would complicate the schema and the `taskq.fail` logic. The `max_retries` per task is sufficient for most use cases.\n\n**Summary:**\n- The retry policy is simple: `max_retries` (default 3) and `backoff_ms` (default 1000 ms) with exponential backoff and jitter.\n- The `taskq.fail` and `taskq.dead` functions implement this policy.\n- The `taskq.pull` loop re-pulls the same `task_id` (if `retry_count < max_retries`).\n- The `taskq.dead` state ensures that the task is set aside for human inspection.\n\n---\n\n## Crash Recovery\n\n**What happens when a worker is killed:**\n- If a worker is killed (e.g., `SIGKILL`, power loss) while a task is `running`, the `task_id` remains `running` and `claimed_at` is set.\n- On restart, `taskq.pull` will see the `running` task (since `status` is still `running`) and will re-claim it (by updating `status` back to `pending` and resetting `claimed_at`).\n- This ensures that no task is permanently stuck.\n\n**How `taskq.pull` handles `running` tasks:**\n- `taskq.pull` uses `SELECT ...
