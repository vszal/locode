If `retries == 0`, the task is marked `dead` (see below).\n- The `dead` state means the task will never be retried again; it is set aside for human inspection (e.g., via `get_task`).\n\n### Backoff algorithm\n- When a task is marked `failed`, its `next_run` is set to `current_time + backoff(retries)`, where `backoff(n)` = `min(2^n * base_delay, max_delay)`.\n- Default parameters: `base_delay = 1` second, `max_delay = 60` seconds, `max_retries = 5`.\n- This yields an exponential backoff: 1s, 2s, 4s, 8s, 16s, then capped at 60s for the final retry.\n- The backoff ensures that a failing dependency (e.g., a downstream service) is not hammered with rapid retries, giving it time to recover.\n\n### Why exponential backoff?\n- It is simple to implement and reason about, and it matches the common pattern used by many systems (e.g., AWS Lambda retries, Kubernetes `backoffLimit`). It provides a smooth increase in wait time as the number of failures grows, which is exactly what we want: early failures are likely transient, so we retry quickly; later failures are more likely to be persistent, so we back off longer.\n- Alternatives (fixed delay, Fibonacci, random jitter) were considered but rejected because they either add unnecessary complexity (random jitter) or risk overloading the system (fixed delay) or under-retrying (Fibonacci grows too fast for modest throughput). Exponential backoff strikes the right balance for the modest throughput target (hundreds of tasks per second).\n\n## Crash Recovery\n\n### What a crash looks like\n- A worker thread may be killed by SIGKILL, a power loss, or a Python interpreter abort. In all cases, the thread disappears, but the SQLite database remains intact (SQLite is designed to survive abrupt shutdowns).\n- The `tasks` table may contain rows in `pending` or `failed` state that were claimed by the crashed thread but not yet executed (or partially executed). However, because we use `FOR UPDATE` and the `next_run` check, a crashed thread cannot hold a task beyond its TTL (see below), and any task that was claimed will be automatically released when the thread dies.\n\n### How recovery works\n1. **No lingering claims**: When a worker thread is killed, the OS reclaims its resources, including any database locks. SQLite's `FOR UPDATE` ensures that a task is only locked for the duration of the transaction. If the transaction is not committed (e.g., the thread dies before `COMMIT`), the lock is released immediately, and the task becomes available again.\n2. **TTL (time-to-live) on claims**: Even if a thread somehow holds a task for a long time (e.g., due to a bug), we enforce a maximum claim duration. In the worker loop, after claiming a task, we set `next_run` to `current_time + claim_ttl` (default 30 seconds). If the thread crashes before the TTL expires, the next worker iteration will see `next_run <= now` and will re-claim the task (if it hasn't been executed yet). This guarantees that a crashed worker cannot permanently block a task.\n3. **Dead tasks are never retried**: If a task has exhausted its retries (`retries == 0`) and is marked `dead`, it will never be re-claimed, regardless of crashes. This is intentional: a task that has failed repeatedly is likely a permanent failure, and we want to preserve it for human inspection rather than waste resources retrying it.\n4. **Manual recovery**: Operators can inspect `get_task(task_id)` to see the payload and status of any task, including those that are `dead`. They can then manually delete the task (via `delete_task`) if they have resolved the issue, or leave it as a record of failure.\n\n### Guarantees\n- **No task is lost**: Every enqueued task is stored in the database immediately (via `INSERT` with `ON CONFLICT DO UPDATE` for idempotency). Even if the process crashes before the task is executed, the task remains in the database and will be retried (or marked dead) as appropriate.\n- **No task is executed twice**: The `FOR UPDATE` claim ensures exclusive ownership, and the `idempotency_key` check ensures that a task with the same logical key will not be executed again if another task with that key is already in `failed` or `dead` state.\n- **No task is stuck forever**: The TTL on claims and the automatic re-claim on the next worker loop guarantee that a crashed worker cannot hold a task beyond a bounded time.\n\n## Failure Modes and How the Design Handles Them\n\n| Failure mode | Description | How the design handles it |\n|--------------|-------------|---------------------------|\

Each value is the number of tasks in that state (integer). `running` is always 0 in this design because workers never transition a task to a \"running\" state; they either claim it and immediately execute it, or they skip it. `scheduled` counts tasks with a `next_run` in the future.\n\n### `taskq.get_task(task_id: int) -> Optional[dict]`\n\nRetrieves a task by its ID.\n\n- **Parameters**\n  - `task_id`: The integer ID returned by `enqueue`.\n\n- **Returns**\n  - A dict with keys `id`, `name`, `payload`, `status`, `retries`, `idempotency_key`, `next_run` (if set), or `None` if the task does not exist.\n\n### `taskq.delete_task(task_id: int) -> bool`\n\nDeletes a task (e.g., after manual inspection).\n\n- **Returns**\n  - `True` if the task was deleted, `False` otherwise.\n\n## Persistence Schema\n\nAll data is stored in a single SQLite database file (default `taskq.db`). The schema is defined in `taskq/schema.sql` and is created automatically on first use.\n\n### `tasks` table\n\n| Column         | Type         | Description |\n|----------------|--------------|-------------|\n| `id`           | INTEGER PRIMARY KEY AUTOINCREMENT | Unique task identifier. |\n| `name`         | TEXT NOT NULL | Task name (handler lookup key). |\n| `payload`      | TEXT NOT NULL | JSON-encoded payload (must be serializable). |\n| `status`       | TEXT NOT NULL | One of `pending`, `failed`, `dead`. |\n| `retries`      | INTEGER NOT NULL DEFAULT 0 | Number of retry attempts remaining (decrements on each failure). |\n| `idempotency_key` | TEXT | Optional key for deduplication. If set, the task will not be executed if another task with the same key is already in `failed` or `dead` state. |\n| `next_run`     | INTEGER | Unix timestamp (seconds since epoch) when the task becomes runnable again (used for delayed execution). `NULL` means immediately runnable. |\n\n**Indexes** (created automatically by SQLite for performance):\n- `idx_tasks_status` on `status` (used by workers to filter by state).\n- `idx_tasks_next_run` on `next_run` (used to find scheduled tasks).\n- `idx_tasks_idempotency_key` on `idempotency_key` (used for deduplication checks).\n\n**Constraints**:\n- `status` is a CHECK constraint: `status IN ('pending', 'failed', 'dead')`.\n- `retries` is a CHECK constraint: `retries >= 0`.\n- `next_run` is a CHECK constraint: `next_run IS NULL OR next_run >= strftime('%s', 'now')` (i.e., not in the past).\n\n**Durability guarantees**:\n- SQLite uses WAL (Write-Ahead Logging) by default, so commits are atomic and visible to readers immediately after a `COMMIT`. Workers always read with `BEGIN IMMEDIATE` (or `BEGIN EXCLUSIVE`) to ensure they see the latest committed state and to prevent readers from seeing partially written rows.\n- The `FOR UPDATE` clause in the claim query ensures that a task can be claimed by only one worker at a time, and that the claim is atomic with respect to the `next_run` and `idempotency_key` checks.\n\n## Retries and Backoff\n\n### Retry policy (per task)\n- Each task has a `retries` counter, initialized to `max_retries` (default 5) when enqueued.\n- On a successful execution, `retries` is decremented (or set to 0) and the task status becomes `pending` again (if `retries > 0`).\n- On a failure (handler raises), `retries` is decremented. If `retries == 0`, the task is marked `dead` (see below).\n- The `dead` state means the task will never be retried again; it is set aside for human inspection (e.g., via `get_task`).\n\n### Backoff algorithm\n- When a task is marked `failed`, its `next_run` is set to `current_time + backoff(retries)`, where `backoff(n)` = `min(2^n * base_delay, max_delay)`.\n- Default parameters: `base_delay = 1` second, `max_delay = 60` seconds, `max_retries = 5`.\n- This yields an exponential backoff: 1s, 2s, 4s, 8s, 16s, then capped at 60s for the final retry.\n- The backoff ensures that a failing dependency (e.g., a downstream service) is not hammered with rapid retries, giving it time to recover.\n\n### Why exponential backoff?\n- It is simple to implement and reason about, and it matches the common pattern used by many systems (e.g., AWS Lambda retries, Kubernetes `backoffLimit`). It provides a smooth increase in wait time as the number of failures grows, which is exactly what we want: early failures are likely transient, so we retry quickly; later failures are more likely to be persistent, so we back off longer.\n- Alternatives (fixed delay, Fibonacci, random jitter) were considered but rejected because they either add unnecessary complexity (random jitter) or risk overloading the system (fixed delay) or under-retrying (Fibonacci grows too fast for modest throughput). Exponential backoff strikes the right balance for the modest throughput target (hundreds of tasks per second).\n\n## Crash Recovery\n\n### What a crash looks like\n- A worker thread may be killed by SIGKILL, a power loss, or a Python interpreter abort. In all cases, the thread disappears, but the SQLite database remains intact (SQLite is designed to survive abrupt shutdowns).\n- The `tasks` table may contain rows in `pending` or `failed` state that were claimed by the crashed thread but not yet executed (or partially executed). However, because we use `FOR UPDATE` and the `next_run` check, a crashed thread cannot hold a task beyond its TTL (see below), and any task that was claimed will be automatically released when the thread dies.\n\n### How recovery works\n1. **No lingering claims**: When a worker thread is killed, the OS reclaims its resources, including any database locks. SQLite's `FOR UPDATE` ensures that a task is only locked for the duration of the transaction. If the transaction is not committed (e.g., the thread dies before `COMMIT`), the lock is released immediately, and the task becomes available again.\n2. **TTL (time-to-live) on claims**: Even if a thread somehow holds a task for a long time (e.g., due to a bug), we enforce a maximum claim duration. In the worker loop, after claiming a task, we set `next_run` to `current_time + claim_ttl` (default 30 seconds). If the thread crashes before the TTL expires, the next worker iteration will see `next_run <= now` and will re-claim the task (if it hasn't been executed yet). This guarantees that a crashed worker cannot permanently block a task.\n3. **Dead tasks are never retried**: If a task has exhausted its retries (`retries == 0`) and is marked `dead`, it will never be re-claimed, regardless of crashes. This is intentional: a task that has failed repeatedly is likely a permanent failure, and we want to preserve it for human inspection rather than waste resources retrying it.\n4. **Manual recovery**: Operators can inspect `get_task(task_id)` to see the payload and status of any task, including those that are `dead`. They can then manually delete the task (via `delete_task`) if they have resolved the issue, or leave it as a record of failure.\n\n### Guarantees\n- **No task is lost**: Every enqueued task is stored in the database immediately (via `INSERT` with `ON CONFLICT DO UPDATE` for idempotency). Even if the process crashes before the task is executed, the task remains in the database and will be retried (or marked dead) as appropriate.\n- **No task is executed twice**: The `FOR UPDATE` claim ensures exclusive ownership, and the `idempotency_key` check ensures that a task with the same logical key will not be executed again if another task with that key is already in `failed` or `dead` state.\n- **No task is stuck forever**: The TTL on claims and the automatic re-claim on the next worker loop guarantee that a crashed worker cannot hold a task beyond a bounded time.\n\n## Failure Modes and How the Design Handles Them\n\n| Failure mode | Description | How the design handles it |\n|--------------|-------------|---------------------------|\n| **Transient network or service failure** | A handler calls an external service that is temporarily unavailable. | The handler raises an exception, which is caught by the worker loop.
