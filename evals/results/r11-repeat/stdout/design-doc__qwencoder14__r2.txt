The initial delay is 1 second, and it doubles with each subsequent retry. After a task fails five times, it is marked as 'dead' and set aside for human inspection.\n\n## Crash Recovery\n\nA task that is claimed by a worker is marked with a `claim_expiry` timestamp. If a worker is killed, the task becomes runnable again once the claim expiry time is reached. This ensures that no task is stuck claimed forever.\n\n## Failure Modes and Handling\n\n- **Duplicate Work**: Tasks are identified by a unique name and payload. If a task with the same name and payload is enqueued again, it is ignored.\n- **Task Failures**: Tasks that fail are retried with backoff. After five retries, the task is marked as 'dead'.\n\n## Trade-offs Rejected\n\n- **Complexity vs. Performance**: The design prioritizes simplicity and reliability over advanced features like priority classes or task cancellation. This allows for easier maintenance and better throughput.\n- **Resource Usage**: The use of SQLite ensures durability without requiring a separate database server, but it may not scale to millions of tasks per second. The throughput target is set to hundreds of tasks per second.\n\n## Observability\n\nThe library provides observability through the following metrics:\n\n- `pending_tasks`: Number of tasks waiting to be processed.\n- `running_tasks`: Number of tasks currently being processed.\n- `failed_tasks`: Number of tasks that have failed.\n- `dead_tasks`: Number of tasks that have been marked as 'dead'.\n\nThis design ensures that the `taskq` library meets the specified requirements while maintaining simplicity and reliability."}}
