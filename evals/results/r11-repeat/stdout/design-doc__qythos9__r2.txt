{"name": "write_file", "args": {"path": "DESIGN.md", "content": "# taskq Design Document\n\n## Overview\n\n`taskq` is a durable, single-process task queue built on SQLite. It provides a simple API for enqueuing background work, processing it with worker threads, and guaranteeing that no task is lost even if the process crashes. The design is intentionally scoped to one machine, one database file, and one or more worker threads inside the same process.\n\nThe core approach is to treat the SQLite database as the single source of truth. All state transitions (enqueue, claim, complete, fail, dead) are expressed as atomic transactions. Workers never inspect the database directly; they only claim a task via an atomic `SELECT ... FOR UPDATE` and then run the handler. This ensures that two workers can never claim the same task simultaneously. Crash recovery is handled by a periodic \"reclaim\" worker that scans for tasks that were claimed but never completed (or failed) and returns them to the pending queue. Retries are implemented with an exponential backoff, and a task is considered permanently failed after a configurable number of consecutive retries (default 5).\n\n## Public API\n\n### `taskq.init(db_path: str, max_retries: int = 5, retry_base: float = 1.0, reclaim_interval: int = 60) -> None`\n\nInitializes the queue. The `max_retries` parameter sets how many times a task will be retried before being marked dead. `retry_base` is the base delay in seconds for exponential backoff. `reclaim_interval` is how often (in seconds) the reclaim worker runs.\n\n### `taskq.enqueue(name: str, payload: dict, delay: float = 0.0) -> str`\n\nEnqueues a new task. `name` is a string identifying the handler function to run. `payload` is a JSON-serializable dict. `delay` is a non-negative float representing seconds to wait before the task becomes eligible for claiming. It contains three tables:\n\n- `tasks` – the canonical record of every task ever enqueued. Columns: `task_id`, `old_status`, `new_status`, `attempt`, `timestamp`.\n\nAll writes go through a single `DB` helper that wraps `sqlite3` with `PRAGMA journal_mode=WAL` and `PRAGMA synchronous=NORMAL`. The `DB` exposes a `commit()` method that is called after every logical operation, ensuring durability.\n\n## Retries and Backoff\n\nWhen a handler raises an exception, `taskq` treats it as a failure and schedules a retry. The number of retries is limited by `max_retries` (default 5). Each retry is delayed by an exponential backoff: `delay = retry_base * (2 ** attempt)`. The `retry_base` defaults to 1 second. The `next_retry_at` column stores the absolute timestamp when the task becomes eligible again. The backoff is per-task, not per-handler, so a flaky external API will not hammer it once it is retried.\n\n## Crash Recovery\n\nA worker that is killed mid-run leaves its task in `running` status with a `claimed_at` timestamp. The reclaim worker runs every `reclaim_interval` seconds (default 60). It scans for tasks where `status = 'running'` and `claimed_at` is older than `reclaim_interval`. For each such task it atomically updates `status` back to `pending` and clears `claimed_at`. This guarantees that no task is ever stuck forever.\n\n## Failure Modes and Handling\n\n- **Duplicate claim**: prevented by `SELECT ... FOR UPDATE` on the `tasks` row; only one worker can acquire the lock.\n- **Process crash while running**: handled by the reclaim worker as described above.\n- **Handler raises after max retries**: the task is marked `dead` and never retried; it remains in the database for inspection.\n- **Race between enqueue and claim**: `enqueue` inserts a new row with `status = pending` and returns its ID; `claim` only selects rows where `status = pending`. Because inserts are atomic, a task cannot be claimed twice.\n- **Corrupt database**: SQLite’s journaling and WAL mode mitigate this; `taskq` does not implement custom corruption recovery beyond re-creating the schema and re-reading audit logs.\n\n## Trade-offs Rejected\n\n- **In-memory queue with periodic flush**: rejected because a crash could lose all pending tasks; durability is a core requirement.\n- **Per-task file locks**: rejected because they do not scale and complicate multi-threaded workers.\n- **Priority queues**: rejected because the spec does not require them and they would add unnecessary complexity.\n- **Cron-style scheduling**: rejected because the spec explicitly excludes scheduled cron expressions.\n- **Web UI**: rejected because it is out of scope.\n\nAll design decisions are made to satisfy the explicit requirements in SPEC.md while staying within the constraints of a single-process, SQLite-backed library.\n"}}
