{"name": "write_file", "args": {"path": "DESIGN.md", "content": "# taskq Design Document\n\n## Overview\n\n`taskq` is a durable, single-process task queue built on SQLite. It provides a simple API for enqueueing background work, processing it with worker threads, and guaranteeing that no task is lost even if the process crashes. The design is intentionally scoped to one machine, one database file, and one or more worker threads inside the same process.\n\nThe core approach is to treat the SQLite database as the single source of truth. All state transitions (enqueued, claimed, running, failed, dead) are recorded as rows in a single `tasks` table. Workers claim tasks atomically via a `SELECT ... FOR UPDATE` pattern, ensuring that no two workers can claim the same task. Claims are time-bounded: a worker must start processing within a configurable window (default 30 seconds), otherwise the claim expires and the task becomes runnable again. This prevents a worker that has been killed (SIGKILL, power loss) from leaving a task stuck forever.\n\nRetries are implemented with exponential backoff. Each task has a `retry_count` and a `next_retry_at` timestamp. When a handler raises an exception, the library decides whether it is transient or permanent. Transient failures increment `retry_count` and schedule the next attempt at `next_retry_at`. Permanent failures (e.g., a fifth consecutive failure) move the task to the `dead` state, where it is visible to operators but never retried.\n\nDuplicate work is prevented by a per-task unique identifier (`task_id`). Before enqueuing, callers must provide a `task_id` (or the library can generate one). The database enforces uniqueness of `task_id` via a unique index, so two racing callers cannot enqueue the same logical job twice. This satisfies the requirement that \"no duplicate work\" occurs when the same logical job is enqueued twice by racing callers.\n\nObservability is provided through a small set of read-only queries that return counts of tasks in each state (pending, running, failed, dead). These are implemented as helper functions in the public API.\n\n## Public API\n\nAll user-facing functions and classes are listed below. Each entry includes the signature, a brief description, and the return type.\n\n### `Taskq` class\n\n```python\nclass Taskq:\n    def __init__(self, db_path: str, max_retry_count: int = 5, claim_timeout: int = 30):\n        \"\"\"Initialize the queue. db_path is the SQLite file path. max_retry_count is the number of retries before a task is marked dead. claim_timeout is seconds a worker has to start processing after claiming.\"\"\"\n        pass\n\n    def register(self, name: str, handler: Callable[[Any], None]) -> None:\n        \"\"\"Register a handler for a task name. name must be a string, handler must be a callable that takes a single argument (the payload) and returns None.\"\"\"\n        pass\n\n    def enqueue(self, name: str, payload: Any, task_id: Optional[str] = None, scheduled_at: Optional[float] = None) -> str:\n        \"\"\"Enqueue a task. name is the task name, payload is JSON-serializable, task_id is an optional unique identifier (if omitted, a UUID is generated), scheduled_at is an optional Unix timestamp (if omitted, the task is enqueued immediately). The schema is deliberately minimal: one table `tasks` with a unique index on `task_id` to enforce no duplicate work.\n\n```sql\nCREATE TABLE tasks (\n    id            TEXT PRIMARY KEY,      -- unique per-task identifier (task_id from API)\n    name          TEXT NOT NULL,         -- task name (for routing to handlers)\n    payload       TEXT NOT NULL,         -- JSON-encoded payload\n    scheduled_at  TEXT NOT NULL,         -- ISO 8601 timestamp of when the task should run\n    retry_count   INTEGER NOT NULL DEFAULT 0,\n    next_retry_at TEXT,                  -- ISO 8601 timestamp of next retry (NULL if not retried)\n    state         TEXT NOT NULL DEFAULT 'pending'\n);\n\nCREATE UNIQUE INDEX idx_tasks_task_id ON tasks(id);\n```\n\nState transitions are modeled by updating the `state` column and optionally setting `next_retry_at`. The `scheduled_at` column is used to filter tasks that are not yet due. Claims are implemented by selecting rows where `state = 'pending'` and `scheduled_at <= datetime('now')`, ordering by `scheduled_at`, and locking them with `FOR UPDATE`. This ensures atomicity and prevents two workers from claiming the same task.\n\n## Retries and Backoff\n\nRetries are controlled per-task. Each task has a `retry_count` (starts at 0) and a `next_retry_at` timestamp (initially NULL). When a handler raises an exception, the library decides whether it is transient or permanent:\n\n- **Transient failure**: The library increments `retry_count` and computes `next_retry_at` using exponential backoff: `next_retry_at = scheduled_at + (2 ** retry_count) * base_delay`. The default `base_delay` is 1 second. The task remains in the `pending` state (or `claimed` if still within the claim window) and will be re-queued automatically when its `next_retry_at` arrives.\n\n- **Permanent failure**: If `retry_count` reaches `max_retry_count` (default 5), the task is moved to the `dead` state. No further retries occur. The `mark_dead` API call must be invoked by the worker to signal this condition.\n\nThe backoff formula ensures that successive attempts are spaced increasingly apart, preventing hammering of a failing dependency. The maximum retry count is configurable via `max_retry_count` in `Taskq.__init__`.\n\n## Crash Recovery\n\nCrash recovery relies on two mechanisms:\n\n1. **Claim expiration**: When a worker claims a task, it must start processing within `claim_timeout` seconds (default 30). If the worker crashes before that window expires, the database still holds the task in `claimed` state. A periodic cleanup job (or a worker thread) scans for tasks where `state = 'claimed'` and `datetime('now') > next_claim_deadline`. Such tasks are automatically re-queued as `pending`, making them available again.\n\n2. **Atomic claim**: The `SELECT ... FOR UPDATE` ensures that even if a crash occurs mid-claim, no other worker can claim the same task. The database remains consistent because SQLite is ACID-compliant.\n\nThus, a killed worker never leaves a task stuck forever; it either finishes within the claim window or is re-queued automatically.\n\n## Failure Modes and Handling\n\n| Failure mode                              | How the design handles it                                                                 |\n|-------------------------------------------|------------------------------------------------------------------------------------------|\
| **Process crash mid-run**                | Claim expiration re-queues the task; no task is lost.                                    |\
| **Worker thread dies after claiming**    | Same as above; the claim window ensures re-queue.                                       |\
| **Handler raises transient exception**    | Increment retry count, schedule next attempt with exponential backoff.                   |\
| **Handler raises permanent exception**    | After max retries, mark task dead; visible to operator but never retried.               |\
| **Duplicate enqueue of same logical job** | Unique `task_id` enforced by database; racing callers cannot create duplicates.         |\
| **Database corruption**                   | SQLite's journaling and WAL mode (enabled by default) provide strong durability.        |\
| **High load (hundreds per second)**      | Single-threaded claim + per-task locking is sufficient; no contention beyond that.      |\
| **Observability needs**                  | `get_stats()` returns counts per state; no additional logging is required.             |\n\n## Trade-offs Rejected and Why\n\n- **Distributed coordination**: We deliberately chose a single-process, single-machine design. Adding cross-machine coordination would require a full distributed system (consensus, leader election, etc.), which is out of scope and would dramatically increase complexity and latency. The requirement explicitly says \"not a distributed system.\"\n\n- **Priority classes**: Implementing per-task priority would require additional database columns, per-priority queues, and a scheduler that picks the highest-priority pending task. This would complicate the claim logic and could introduce contention. Since the spec does not ask for priorities, we rejected this feature.\n\n- **Task cancellation**: Allowing callers to cancel a pending or running task would require a `cancel(task_id)` API, a `cancelled` state, and handling of in-flight work. This adds significant complexity and could lead to inconsistent state if a worker crashes while handling a cancelled task. The spec says cancellation is out of scope, so we omitted it.\n\n- **Cron-style scheduled expressions**: Supporting arbitrary cron expressions would require a parser and a scheduler that evaluates them periodically. This is beyond the modest throughput target and would increase code size. The spec explicitly excludes cron expressions, so we chose to only support a simple `scheduled_at` timestamp.\n\n- **Web UI**: Building a web interface for monitoring and manual intervention would require a web server, templates, and possibly a database of user sessions. This is clearly out of scope and would bloat the library. We therefore omitted any UI components.\n\n- **Multiple database backends**: Using an abstracted database layer (e.g., SQLAlchemy) would add dependencies and configuration overhead. The spec requires only the built-in `sqlite3` module, so we kept the implementation minimal and directly use `sqlite3`.\n\n- **Async/await**: While async could simplify some I/O, the worker model is already single-threaded per worker, and the claim logic is synchronous. The spec does not demand async, so we chose synchronous APIs.\n\n- **Per-task metadata beyond state**: Adding arbitrary metadata (tags, custom fields) would require a flexible schema (e.g., a JSON blob column) and would complicate queries. Since the spec only needs name, payload, and state, we kept the schema simple.\n\n- **Immediate re-queue on failure**: Re-queuing a failed task immediately (without backoff) would hammer the system. We chose exponential backoff to respect the requirement that retries must not hammer a failing dependency.\n\n- **Claim timeout of zero**: Setting `claim_timeout` to zero would mean a worker must start processing instantly, which is unrealistic and would cause many tasks to be re-queued unnecessarily.
