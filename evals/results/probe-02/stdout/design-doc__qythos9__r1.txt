{"name": "write_file", "args": {"path": "DESIGN.md", "content": "# taskq Design Document\n\n## Overview\n\n**taskq** is a durable, in-process task queue for Python 3.10+. It provides a simple API for enqueueing background work, with built-in persistence via SQLite, atomic claiming, exponential backoff retries, and crash recovery. It is deliberately scoped to a single process with one SQLite file and multiple worker threads.\n\n**Core approach**: All state lives in a single SQLite database with three tables (`tasks`, `task_claims`, `task_stats`). Workers acquire a task atomically via a `SELECT ... FOR UPDATE` on the `tasks` table, which both marks the task as claimed and atomically increments the `claimed_count`. Claims are tied to a short-lived `task_claims` row that expires after a fixed window (default 30 seconds). If a worker crashes before it can finish the task, the claim expires and the task becomes runnable again. Retries are implemented with exponential backoff; after a configurable maximum number of retries (default 5), the task is marked as dead and set aside for human inspection.\n\n**No duplicate work**: The library enforces idempotency at the task level. When a task is enqueued, its `id` is derived from a monotonic counter stored in the database. If the same logical job is enqueued twice by racing callers, they will receive the same `id` only if they enqueue the same `(name, payload)` tuple at exactly the same instant. In practice, callers should provide an explicit `id` (or a unique identifier) when they want to guarantee no duplicate execution. The library does not attempt to deduplicate based on content; it trusts the caller to provide unique identifiers for idempotent work. This is a deliberate design choice: deduplication based on payload would require hashing and collision handling, which adds complexity and potential for false positives. Instead, the library provides a simple `enqueue(id, name, payload, due_at=None)` API where `id` is the caller's guarantee of uniqueness.\n\n**Handler contract**: Handlers are plain Python callables registered via `register_handler(name, handler)`. A handler receives a single argument: the task payload (a dict). Handlers may raise any exception. If the exception is a `taskq.RetryableError`, the task is retried according to the backoff policy. If the exception is any other type (including `taskq.DeadError`), the task is marked as dead after the maximum retry count is reached. Handlers should not perform long-running I/O; they are expected to complete quickly (under a few seconds) to keep throughput high.\n\n**Throughput**: The design targets hundreds of tasks per second. SQLite is sufficient for this scale; we do not introduce any locking beyond the database-level row locks. Workers are implemented as threads that loop over `get_next_task()` and call the handler. The loop includes a short sleep after each task to avoid CPU hogging.\n\n**Observability**: The library exposes a `stats()` method that returns a dict with keys `pending`, `running`, `failed`, and `dead`. These counts are derived from the `tasks` table and the `task_claims` table. The `pending` count excludes claimed tasks; `running` counts tasks with an active claim; `failed` counts tasks that have exceeded the retry limit but are not yet dead; `dead` counts tasks that have been permanently failed.\n\n## Public API\n\n### `taskq` package namespace\n\n- `taskq.RetryableError(Exception)` – Base exception for transient failures that should trigger a retry.\n- `taskq.DeadError(Exception)` – Base exception for permanent failures that should stop retries.\n- `taskq.register_handler(name: str, handler: Callable[[dict], None])` – Register a handler for a task name.\n- `taskq.enqueue(id: str, name: str, payload: dict, due_at: Optional[int] = None) -> int` – Enqueue a task. Returns the task `id` (which is also the primary key in the database).\n- `taskq.get_stats() -> dict` – Return current queue statistics.\n- `taskq.shutdown()` – Signal that no more tasks will be enqueued; workers will finish their current tasks and exit.\n\n### `taskq` functions (module-level)\n\n- `register_handler(name: str, handler: Callable[[dict], None])` – Same as above; provided at module level for convenience.\n- `enqueue(id: str, name: str, payload: dict, due_at: Optional[int] = None) -> int` – Same as above.\n- `get_stats() -> dict` – Same as above.\n- `shutdown()` – Same as above.\n\n### `taskq` exceptions (module-level)\n\n- `RetryableError(Exception)` – Same as above.\n- `DeadError(Exception)` – Same as above.\n\n## Persistence Schema\n\nThree tables in a single SQLite database (`taskq.db`):\n\n### `tasks`\n| Column | Type | Description |\n|--------|------|-------------|\n| `id` | INTEGER PRIMARY KEY AUTOINCREMENT | Unique task identifier (monotonic counter). |\n| `name` | TEXT NOT NULL | Task name (used to lookup the handler). |\n| `payload` | TEXT NOT NULL | JSON-encoded payload (UTF-8). |\n| `due_at` | INTEGER | Unix timestamp; `NULL` means immediately runnable. |\n| `status` | TEXT NOT NULL | One of `pending`, `claimed`, `failed`, `dead`. |\n| `retry_count` | INTEGER NOT NULL DEFAULT 0 | Number of times this task has been retried. |\n| `max_retries` | INTEGER NOT NULL DEFAULT 5 | Maximum allowed retries (configurable per task). |\n| `claimed_by` | TEXT | Thread ID (or `NULL` if unclaimed). |\n| `claimed_at` | INTEGER | Unix timestamp when claimed. |\n| `expires_at` | INTEGER | Unix timestamp when the claim expires (null if never claimed). |\n\n**Indexes**:\n- `idx_tasks_due_at` on `(due_at)` for fast lookup of scheduled tasks.\n- `idx_tasks_status_pending` on `(status)` for counting pending tasks.\n- `idx_tasks_status_claimed` on `(status)` for counting claimed tasks.\n\n### `task_claims`\n| Column | Type | Description |\n|--------|------|-------------|\n| `id` | INTEGER PRIMARY KEY AUTOINCREMENT | Claim identifier (not used for logic). |\n| `task_id` | INTEGER NOT NULL UNIQUE | Foreign key to `tasks.id`. |\n| `worker_id` | TEXT NOT NULL | Identifier of the worker thread that claimed it. |\n| `claimed_at` | INTEGER NOT NULL | Unix timestamp when claimed. |\n| `expires_at` | INTEGER NOT NULL | Unix timestamp when the claim expires (always set). |\n\n**Indexes**:\n- `idx_claims_task_id` on `(task_id)` for fast lookup of claimed tasks.\n- `idx_claims_worker_id` on `(worker_id)` for counting claims per worker.\n\n### `task_stats`\n| Column | Type | Description |\n|--------|------|-------------|\n| `key` | TEXT PRIMARY KEY | One of `pending`, `running`, `failed`, `dead`. |\n| `value` | INTEGER NOT NULL | Count of tasks in that state. |\n\n**Indexes**:\n- None; this table is tiny and accessed via primary key.\n\n**Invariant**: The sum of `value` for keys `pending`, `running`, `failed`, `dead` must equal the total number of rows in `tasks`. This invariant is enforced by a trigger on `tasks` that updates `task_stats` after any row insert, update, or delete.\n\n## Retries and Backoff\n\n**Policy**: Exponential backoff with jitter, capped at a maximum delay.\n\n- **Initial delay**: 0 seconds (first attempt runs immediately).\n- **Backoff formula**: `delay = min(max_delay, base_delay * (2 ** retry_count))`.
- **Jitter**: Add a random value uniformly distributed in `[0, jitter_factor * delay]` to the computed delay.
- **Parameters** (configurable via `taskq.configure()`):\n  - `base_delay`: 1 second (default).\n  - `max_delay`: 60 seconds (default).\n  - `jitter_factor`: 0.2 (default, i.e., up to 20% jitter).\n  - `max_retries`: 5 (default).\n\n**Behavior**: When a handler raises `RetryableError`, the library records the failure, increments `retry_count`, and schedules the next attempt after the computed backoff delay. The worker thread sleeps for that duration before pulling the next task. If the handler raises any other exception (including `DeadError`), the task is marked as failed; after `max_retries` failures, it is marked as dead.\n\n**Rationale**: Exponential backoff is simple, effective, and avoids hammering failing dependencies. Jitter prevents thundering herd when many tasks fail at the same time. The maximum delay caps the backoff to avoid unbounded waits. The maximum retry count ensures that eventually failing tasks are set aside for human inspection.\n\n## Crash Recovery\n\n**Goal**: Ensure that a killed worker does not leave a task permanently claimed.\n\n**Mechanism**: Claims are tied to a short-lived `task_claims` row with an `expires_at` timestamp (default 30 seconds after `claimed_at`). When a worker crashes (SIGKILL, power loss, etc.), the OS terminates the process; the `task_claims` row remains in the database but its `expires_at` is still in the future. The next time any worker calls `get_next_task()`, the library performs a cleanup step: it deletes any `task_claims` rows where `expires_at < now`. This is done atomically via a `DELETE FROM task_claims WHERE expires_at < ?` statement executed at the start of each `get_next_task()` call.\n\n**Result**: After cleanup, the corresponding `tasks` row is unclaimed (status reverts to `pending`), and the task becomes runnable again. No task can be stuck claimed forever.\n\n**Additional safeguards**:\n- The `tasks` table uses `SELECT ... FOR UPDATE` when claiming, which ensures atomicity of the claim and the status update.\n- The `task_stats` trigger updates counts immediately after any row change, so the operator can always see the current state.\n- The `shutdown()` method sets a flag in the database (`shutdown_at`) that workers check before pulling new tasks; they will finish their current claimed tasks and then exit gracefully.\n\n## Failure Modes and Handling\n\n| Failure mode | How it occurs | How the design handles it |\n|--------------|---------------|---------------------------|\
| **Worker crash while claiming** | SIGKILL, power loss, OS kill | Claim expires after 30 seconds; cleanup on next `get_next_task()` unclaims the task. |\
| **Handler raises `RetryableError`** | Transient failure (e.g., network timeout) | Task is retried with exponential backoff; after `max_retries` it is marked dead. |\
| **Handler raises any other exception** | Permanent failure (e.g., logic error) | Task is marked failed; after `max_retries` it is marked dead. |\
| **Database corruption** | Disk failure, power loss during write | SQLite's journal mode (default `WAL`) provides atomic writes; the `task_stats` trigger ensures consistency. If corruption occurs, the operator can inspect the `tasks` table directly; the library does not implement automatic repair. |\
| **Race condition: two workers claim the same task** | Two threads call `get_next_task()` concurrently | `SELECT ... FOR UPDATE` on `tasks` ensures only one thread can acquire the row; the other will wait until the first finishes or the claim expires. |\
| **Duplicate enqueue of the same logical job** | Two callers enqueue the same `(name, payload)` at the same instant | The library does not deduplicate; each enqueue gets a unique `id`. Callers must provide an explicit `id` (or a unique identifier) to guarantee no duplicate execution. |\
| **Task exceeds `max_retries`** | Handler keeps failing | After the last retry, the task is marked dead; it is set aside for human inspection. |\
| **System shutdown while tasks are pending** | OS shutdown, power loss | The shutdown flag is written atomically; workers finish their current claimed tasks and then exit. Pending tasks remain in the database and can be resumed after restart. |\
| **Memory exhaustion** | Too many tasks in memory | The library does not buffer tasks; they are stored directly in SQLite. Memory usage is bounded by the database size. |\
| **Clock skew** | `due_at` timestamps are off | The library uses `time.time()` for `due_at`; if the clock jumps, tasks may be delayed or executed early. This is an acceptable trade-off for simplicity; callers can use monotonic time if they need precise scheduling. |\
\n## Trade-offs Rejected and Why\n\n1. **Distributed coordination** – Rejected. The spec explicitly says \"not a distributed system\"; adding cross-machine coordination would require network code, consensus, and significantly increase complexity and failure surface. The target use case is a single machine with multiple workers, which is fully covered by the current design.\n\n2. **Priority classes** – Rejected. Implementing priorities would require additional fields, sorting, and potentially complex scheduling logic. The throughput target is modest (hundreds per second), so a simple FIFO queue is sufficient. If priorities become necessary, they can be added later without breaking the core design.\n\n3. **Task cancellation** – Rejected. Cancellation would require a separate `cancel(task_id)` API and handling of in-flight tasks. This adds state and complexity. The spec says cancellation is out of scope; we can always add it later if needed.\n\n4. **Scheduled cron expressions** – Rejected. Implementing cron would require parsing and scheduling logic, which is beyond the scope of a simple task queue. The `due_at` field already allows delayed execution; callers can compute their own timestamps if they need cron-like behavior.\n\n5. **Web UI** – Rejected. Observability is provided via the `stats()` method; a web UI would require a server, templates, and authentication. The spec says it is out of scope; we can add a simple CLI tool later if needed.\n\n6. **Content-based deduplication** – Rejected. Deduplicating based on payload would require hashing and collision handling, which adds complexity and potential for false positives. The library trusts callers to provide unique identifiers; this is a simpler and more explicit contract.\n\n7. **Asyncio integration** – Rejected. While asyncio is popular, the spec requires standard library only and multiple worker threads. Using asyncio would require a different event loop and would complicate the thread-safety model. The current design uses plain threads, which are straightforward and fully supported by the standard library.\n\n8. **Journal mode other than WAL** – Rejected. WAL (Write-Ahead Logging) is the default in SQLite and provides the best balance of performance and crash safety for our use case. Switching to `DELETE` or `TRUNCATE` would reduce concurrency and increase the risk of corruption during crashes.\n\n9. **Dynamic retry policies per task** – Rejected. While it would be nice to allow per-task retry policies, implementing that would require additional fields and logic. The spec says retries must not hammer failing dependencies; a simple exponential backoff with a global max retries is sufficient for the target throughput. If per-task policies become necessary, they can be added later without breaking the core design.\n\n10. **Task grouping / batch processing** – Rejected. Grouping tasks would require additional state and logic. The spec does not mention batch processing; each task is independent and can be handled individually. If batch processing becomes necessary, it can be implemented as a higher-level wrapper around the basic API.\n\n## Summary\n\nThe design provides a simple, robust, and thread-safe task queue that meets all the requirements in the spec. It uses SQLite for persistence, atomic claiming with short-lived claims for crash recovery, exponential backoff with jitter for retries, and a clear contract for handlers. All failure modes are either prevented (via atomic operations) or handled gracefully (via claim expiration and dead task marking). The trade-offs rejected are all justified by the spec's constraints and the modest throughput target. The resulting library will be easy to use, easy to extend, and easy to reason about.\n", "replace_all": false}}
