The retry policy is:

1. **Count**: Each retry increments `retry_count` in the `tasks` row.
2. **Backoff**: The `next_run` timestamp is set to `now + retry_base * (2 ** retry_count)`. This is exponential backoff: 1s, 2s, 4s, 8s, etc.
3. **Max retries**: If `retry_count` reaches `max_retries` (default 3), the task is marked `status = 'failed'` and `next_run = NULL`. It will never be retried again.
4. **Dead-letter**: Failed tasks are considered \"dead\" and are visible via `get_status()['failed']`. They are not automatically deleted; they remain in the database for inspection.

### Why exponential backoff?

- **Avoids hammering**: If a downstream service is temporarily overloaded, repeated rapid retries could exacerbate the problem. Exponential backoff gives the system time to recover.
- **Simple and effective**: For modest throughput (hundreds per second), exponential backoff provides a good balance between responsiveness and load.
- **Configurable**: The `retry_base` parameter lets users tune the aggressiveness of retries.

### What happens after max retries?

- The task is marked `status = 'failed'`.
- It is no longer picked up by workers.
- It remains in the database so an operator can inspect the payload and any logs (if we add logging later).
- No further retries occur.

- The process crashes mid-run, leaving the database in an inconsistent state.
- A task is stuck in `running` forever because no worker ever releases it.

### How we handle it\n\n1. **Atomic claim**: When a worker claims a task, it uses a `SELECT ... FOR UPDATE` on the `tasks` row, setting `claimed_by = thread_id` and `status = 'running'`. This guarantees that no other worker can claim the same task concurrently.\n\n2. **Release on completion**: When the handler finishes (whether successfully or after a retry), the worker explicitly updates the row: `status = 'pending'` (if it will be retried) or `status = 'dead'` (if it has exceeded max retries). This clears `claimed_by`.\n\n3. **Periodic cleanup**: At startup (and optionally on a timer), the system scans for any rows where `status = 'running'` and `claimed_by` is not NULL. For each such row, it resets `status = 'pending'` and clears `claimed_by`. This ensures that any orphaned claim is quickly recovered.\n\n4. **No long-lived locks**: Because SQLite uses row-level locks and we always release the lock immediately after updating the row, there is no risk of a lock being held forever.\n\n### Guarantees\n\n- **No task is ever lost**: Even if a worker crashes, the task remains in the database and will be re-queued.\n- **No duplicate execution**: Because claims are atomic and cleared on completion, a task can never be processed twice.\n- **Fast recovery**: The cleanup loop runs immediately on process restart, so orphaned tasks are recovered within seconds.\n\n---\n\n## Failure Modes and How We Handle Them\n\n| Failure mode | What happens | How we handle it |\n|--------------|--------------|------------------|\n| **Worker crash while running** | Task remains `running` with `claimed_by` set. | Periodic cleanup resets it to `pending`. |\n| **Process killed mid-run** | Same as above. | Same cleanup. |\n| **Handler raises exception** | Task is retried with backoff. | Exponential backoff, max retries, then dead. |\n| **Duplicate enqueue of same logical job** | Two identical tasks are created. | Not prevented; the system will run both.
