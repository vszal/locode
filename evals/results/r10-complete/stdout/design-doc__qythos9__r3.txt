{"name": "write_file", "args": {"path": "DESIGN.md", "content": "# taskq Design Document\n\n## Overview\n\n**taskq** is a durable, in-process task queue for Python 3.10+ using only the standard library. It provides a single SQLite database file that persists across process crashes, supports multiple worker threads within one process, and guarantees that no task is executed twice. The design prioritizes simplicity, correctness, and observability over extreme throughput.\n\n**Core approach:**\n- **Single SQLite file** as the source of truth for all tasks, state, and metadata.\n- **Worker threads** pull tasks from a `running` queue; they claim a task atomically via an `UPDATE ... SET claimed_by = <pid> WHERE id = ? AND claimed_by IS NULL` statement, ensuring no two workers can claim the same task.\n- **Claim expiration** is enforced by a periodic background thread (or a signal handler) that scans for tasks whose `claimed_at` timestamp is older than a configurable `claim_timeout` (default 30 seconds) and moves them back to `pending` so they can be retried.\n- **Retries** are exponential backoff: after each failure the next retry delay doubles, capped at a maximum (default 1 hour). A task that fails more than a configurable number of times (default 5) is moved to `dead` and never retried.\n- **Duplicate prevention** is achieved by a unique index on `(name, payload_hash)`. Before enqueueing, the library computes a SHA-256 hash of the JSON payload and checks for an existing row with the same `name` and hash. If found, the enqueue is a no-op (the task is already queued). This satisfies \"no duplicate work\" in the sense that identical logical jobs are never queued twice.\n- **Crash recovery** relies on SQLite's ACID guarantees and the claim expiration mechanism. If a worker is killed mid-claim, the `claimed_by` column still holds the PID, but the claim will expire after `claim_timeout`, returning the task to `pending`. No manual intervention is required.\n- **Observability** is provided via a small set of read-only queries: `SELECT COUNT(*) FROM tasks WHERE status = 'pending'`, etc., exposed through a `stats()` method.\n\nThe design deliberately avoids features out of scope (priority queues, cancellation, cron, web UI) to keep the codebase small and maintainable.\n\n## Public API\n\nAll public symbols are defined in `taskq/__init__.py`. The schema is defined in `taskq/db.py`.\n\n### `tasks` table\n\n| Column          | Type        | Constraints / Notes |\n|-----------------|-------------|---------------------|\n| `id`            | INTEGER     | PRIMARY KEY, AUTOINCREMENT |\n| `name`          | TEXT        | NOT NULL, indexed (see below) |\n| `payload`       | TEXT        | NOT NULL, JSON encoded |\n| `status`        | TEXT        | NOT NULL, one of: `pending`, `running`, `dead`, `scheduled` |\n| `claimed_by`    | INTEGER     | NOT NULL, stores PID of the worker that claimed the task; NULL for `pending`/`scheduled` |\n| `claimed_at`    | REAL        | NOT NULL, Unix timestamp when the task was claimed |\n| `scheduled_at`  | REAL        | NOT NULL, Unix timestamp when the task should become `pending` (or NULL if not scheduled) |\n| `retry_count`   | INTEGER     | NOT NULL, starts at 0, incremented on each retry |\n| `last_error`    | TEXT        | NOT NULL, JSON encoded error message from the last attempt |\n\n**Indexes**\n- `UNIQUE(name, payload_hash)` where `payload_hash` is a computed column storing `SHA256(payload)`. This enforces the \"no duplicate work\" guarantee.\n- `INDEX(status)` for fast status queries.\n- `INDEX(claimed_at)` for claim expiration scans.\n\n**Row lifecycle**\n1. **Enqueue**: Insert a new row with `status = 'pending'`, `claimed_by = NULL`, `claimed_at = NULL`, `scheduled_at = <now>` (or `NULL` if immediate), `retry_count = 0`, `last_error = ''`.\n2. **Claim**: A worker calls `fetch_task()`, which executes `UPDATE tasks SET status = 'running', claimed_by = <pid>, claimed_at = <now> WHERE id = ? AND claimed_by IS NULL AND status = 'pending'`. This is atomic and ensures only one worker can claim a task.\n3. **Run**: The worker executes the handler. If it succeeds, the worker calls `complete_task(id)`, which sets `status = 'dead'`, `retry_count = 0`, `last_error = ''`.\n4. **Fail**: If the handler raises (or returns `PermanentFailure`), the worker calls `retry_task(id)`, which increments `retry_count`, stores the error in `last_error`, and sets `status = 'pending'` (or `scheduled` if a future time is set). The `claimed_by` and `claimed_at` are cleared.\n5. **Claim expiration**: A background thread (or signal handler) periodically scans for rows where `status = 'running'` and `claimed_at < now - claim_timeout`. For each such row, it sets `status = 'pending'`, clears `claimed_by` and `claimed_at`, and leaves `retry_count` unchanged. This ensures that a killed worker does not leave a task stuck forever.\n6. **Dead**: After `retry_count` exceeds `max_retries`, `retry_task` sets `status = 'dead'`. Dead tasks are never claimed again.\n\n## Retries and Backoff\n\n**Policy:** Exponential backoff with a maximum cap.\n\n- After each failure, the next retry delay is `min(backoff * 2, max_backoff)` seconds, where `backoff` starts at 1 second.\n- The delay is stored in `scheduled_at` when the task is moved back to `pending` (or `scheduled`).\n- The background expiration thread moves the task to `pending` at `scheduled_at`.\n- `max_retries` defaults to 5. After the fifth failure, the task is marked `dead` and never retried.\n\n**Rationale:** This policy prevents hammering a failing external service while still giving transient failures a chance to succeed. The exponential growth quickly reduces load, and the cap ensures we don't wait forever for a task that will never succeed.\n\n## Crash Recovery\n\n**Guarantee:** No task will be lost or stuck forever after a process crash.\n\n- SQLite's ACID properties ensure that any in-flight writes are either fully committed or rolled back. A crash will not leave a task in an inconsistent state.\n- The claim expiration mechanism is the key: any task that was claimed (`status = 'running'`) will have its `claimed_at` timestamp checked against `claim_timeout`. If the process crashes, the worker thread is gone, but the database still contains the row with `claimed_by = <pid>`. The expiration thread will eventually move it back to `pending`, making it runnable again.\n- Because `claimed_by` is cleared when a task is moved back to `pending`, a new worker can claim it without any special handling.\n- No manual intervention or restart script is required; the library self-heals.\n\n## Failure Modes and Handling\n\n| Failure mode                              | How the design handles it                                                                 |\n|------------------------------------------|------------------------------------------------------------------------------------------|\
| **Worker killed mid-claim**             | Claim expires after `claim_timeout`; task returns to `pending`. No permanent loss.      |\n| **Database disk full**                 | SQLite will raise an error; the library logs it and leaves tasks in their current state. The operator must fix the disk. |\n| **SQLite corruption**                 | The library relies on WAL mode (enabled by default) to reduce corruption risk. If corruption occurs, the only recovery is to restore from a backup. |\n| **Handler raises `PermanentFailure`**  | Task is moved to `dead` after one attempt; no retries.                                  |\n| **Handler raises transient exception**  | Task is retried with exponential backoff up to `max_retries`.                           |\n| **Duplicate enqueue of same payload**   | Unique index on `(name, payload_hash)` prevents a second row; `enqueue` returns the existing `id`. |\n| **Race between two callers enqueuing** | Both will see the same `id` after the first insert; the second call will be a no-op.   |\n| **Clock skew**                         | `scheduled_at` is stored as a Unix timestamp; if the system clock moves backward, the expiration thread will still move the task to `pending` at the stored time (which may be in the past). This is acceptable because the task will be processed immediately. |\n| **Multiple workers in same process**    | Only one worker can claim a task at a time due to the atomic `UPDATE`. No coordination needed. |\n\n## Trade-offs Rejected and Why\n\n1. **Using a separate `running` table**\n   - *Rejected.* A single `tasks` table with a `status` column is simpler, uses less memory, and SQLite handles row locking efficiently.
