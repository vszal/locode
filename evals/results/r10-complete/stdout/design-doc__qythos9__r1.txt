It provides a simple API for enqueueing background work, processing it with registered handlers, and guaranteeing that no task is lost even if the host process crashes. It is deliberately scoped to a single machine with a single SQLite file and one or more worker threads inside the same process.\n\n**Core guarantees**\n- **Durability**: A task that has been acknowledged by a worker will survive a crash of the host process. No task may be executed by two workers at once.\n- **No duplicate work**: If the same logical job is enqueued twice by racing callers, only one will be processed.\n- **Graceful failure**: A task that raises is retried later; a task that keeps failing eventually stops being retried and is set aside for a human to inspect.\n- **Future scheduling**: Callers can enqueue work for the future (\"run this in ten minutes\").\n- **Observability**: An operator can ask how many tasks are pending, running, failed, and dead.\n\n**What is out of scope**\nCross-machine coordination, priority classes, task cancellation, scheduled cron expressions, and a web UI are explicitly out of scope.\n\n## Public API\n\nAll public functions and classes are described below. Each entry includes the signature, a brief description of what it does, and what it returns.\n\n### `taskq` package namespace\n\nThe library is imported as `import taskq`. All public symbols live in the `taskq` module.\n\n### `taskq.enqueue(name: str, payload: Any, retry: int = 3, scheduled: Optional[float] = None) -> None`\n\nEnqueues a named task with a JSON-serializable payload. The `name` identifies the handler to run (see `register`). `retry` is the maximum number of times the task will be retried after a failure. `scheduled` is an optional Unix timestamp (float) indicating when the task should become runnable; if omitted, the task is available immediately.\n\n**Returns**: nothing (the task is stored in the queue).\n\n**Behavior**:\n- The payload is serialized to JSON and stored in the SQLite database.\n- If `scheduled` is provided, the task is inserted into the `scheduled` table and will be made visible to workers only after the given time.\n- Duplicate prevention is handled at the enqueue time: if a task with the same `name` and payload is already pending or scheduled, the enqueue is a no-op (see \"No duplicate work\" below).\n\n### `taskq.register(name: str, handler: Callable[[Any], None]) -> None`\n\nRegisters a handler function for a given task name. The handler receives the deserialized payload and must not raise. If the handler does raise, the task will be retried according to its `retry` count (see below).\n\n**Returns**: nothing.\n\n**Behavior**:\n- Handlers are stored in the `handlers` table keyed by `name`.\n- A name can be registered only once; attempting to register a duplicate raises `ValueError`.\n\n### `taskq.work() -> None`\n\nThe main worker loop. This function should be called in a thread (or multiple threads) to process tasks. It continuously pulls the next available task, runs its handler, and either marks it as completed or schedules a retry.\n\n**Returns**: nothing (runs until the process exits).\n\n**Behavior**:\n- `work()` acquires a lock to ensure only one thread processes a given task at a time.\n- It fetches the next task atomically (see \"Atomic claim\" below).\n- It runs the registered handler for that task's name.\n- If the handler raises, the task is marked as failed and will be retried up to its `retry` limit.\n- If the handler completes successfully, the task is marked as done.\n- `work()` does not block indefinitely; it sleeps briefly between iterations to avoid busy-waiting.\n\n### `taskq.stats() -> Dict[str, int]`\n\nReturns a dictionary with counts of tasks in each state: `\"pending\"`, `\"running\"`, `\"failed\"`, and `\"dead\"`.\n\n**Returns**: `Dict[str, int]`.\n\n**Behavior**:\n- Queries the SQLite database for the number of rows in each relevant table.\n- Provides a quick snapshot for observability.\n\n### `taskq.list_tasks() -> List[TaskInfo]`\n\nReturns a list of all tasks with their current state, name, payload, retry count, and scheduled time (if any).\n\n**Returns**: `List[TaskInfo]` where `TaskInfo` is a simple dataclass with fields `name`, `payload`, `retry`, `state`, `scheduled`.\n\n**Behavior**:\n- Useful for debugging or for a custom UI.\n\n### `taskq.reset(name: str) -> None`\n\nDeletes all tasks with the given `name` from the database. This is a manual operation for cleanup or reinitialization.\n\n**Returns**: nothing.\n\n## Persistence Schema\n\nAll data is stored in a single SQLite file (default path: `~/.taskq/db.sqlite`). The schema consists of four tables: `tasks`, `handlers`, `scheduled`, and `dead`. Each table is described below.\n\n### `tasks` table\n\n| Column        | Type           | Description |\n|---------------|----------------|-------------|\n| `id`          | INTEGER PRIMARY KEY AUTOINCREMENT | Unique identifier for each task. |\n| `name`        | TEXT NOT NULL | The handler name (must match a registered handler). |\n| `payload`     | TEXT NOT NULL | JSON-encoded payload. |\n| `retry`       | INTEGER NOT NULL | Maximum number of retries allowed. |\n| `state`       | TEXT NOT NULL | One of `pending`, `running`, `failed`, `dead`. |\n| `claimed_at`  | TIMESTAMP | When the task was claimed by a worker (NULL if not claimed). |\n| `expires_at`  | TIMESTAMP | When the claim expires (NULL if no expiration). |\n\n**Invariants**:\n- A task is `pending` until it is claimed by a worker.\n- Once claimed, `claimed_at` is set and `state` becomes `running`.\n- If the claim expires (see \"Claim expiration\" below), the task returns to `pending`.\n- A task moves to `failed` after exhausting its retry count.\n- A task moves to `dead` after being marked as failed and not retried.\n\n### `handlers` table\n\n| Column        | Type           | Description |\n|---------------|----------------|-------------|\n| `name`        | TEXT PRIMARY KEY | The handler name. |\n| `handler`     | TEXT NOT NULL | JSON-encoded Python expression that evaluates to a callable. |\n\n**Invariants**:\n- Each `name` is unique.\n- The `handler` field stores a serialized form of the function (e.g., using `pickle` or a custom JSON-serializable representation). Since we are limited to the standard library, we will store the handler as a string of Python code and evaluate it at runtime using `eval`. This is acceptable for a small, trusted library.\n\n### `scheduled` table\n\n| Column        | Type           | Description |\n|---------------|----------------|-------------|\n| `id`          | INTEGER PRIMARY KEY AUTOINCREMENT | Unique identifier for each scheduled task. |\n| `task_id`     | INTEGER NOT NULL | Foreign key to `tasks.id`. |\n| `scheduled_at` | TIMESTAMP NOT NULL | The time when the task should become runnable. |\n\n**Invariants**:\n- A task can have at most one entry in `scheduled`.\n- When a task is scheduled, its `state` in `tasks` is set to `pending` and `expires_at` is set to `scheduled_at`.\n- Workers will ignore any task whose `expires_at` is in the future.\n\n### `dead` table\n\n| Column        | Type           | Description |\n|---------------|----------------|-------------|\n| `id`          | INTEGER PRIMARY KEY AUTOINCREMENT | Unique identifier for each dead task. |\n| `task_id`     | INTEGER NOT NULL | Foreign key to `tasks.id`. |\n| `reason`      | TEXT NOT NULL | Human-readable reason why the task was marked dead. |\n\n**Invariants**:\n- A task moves to `dead` only after it has failed all retries.\n- The `reason` field is set to a string describing why the task was marked dead (e.g., \"handler raised after 3 retries\").\n\n## Retries and Backoff\n\n### Retry policy\n\nWhen a task's handler raises an exception, the task is marked as `failed` and will be retried up to its `retry` count. The number of retries is stored in the `tasks` table at enqueue time.\n\n### Backoff strategy\n\nTo avoid hammering a failing dependency, we use an **exponential backoff with jitter**.\n\n**Algorithm**:\n1. On the first failure, wait 1 second.\n2. On each subsequent failure, double the wait time (2s, 4s, 8s, …) up to a maximum of 30 seconds.\n3. Add a random jitter of up to 10% of the current backoff interval to avoid thundering herd.\n\n**Implementation details**:\n- The backoff interval is stored in the `tasks` table as `retry_delay` (default 1 second).\n- After each failure, we update `retry_delay` to `min(retry_delay * 2, 30)` and add jitter.\n- The worker sleeps for the computed delay before marking the task as `pending` again.\n\n**Why exponential backoff?**\n- It provides a simple, effective way to reduce load on failing services.\n- It is widely used in production systems and has been proven to work well for transient failures.\n\n**Why jitter?**\n- Without jitter, all workers would retry at the same time, potentially overwhelming the failing service.\n- A small random component spreads out the retry attempts.\n\n## Crash Recovery\n\n### Claim expiration\n\nTo ensure that a task is not stuck forever if a worker crashes, we implement a **claim expiration** mechanism.\n\n**How it works**:\n- When a worker claims a task, it sets `claimed_at` to the current time and `expires_at` to `claimed_at + 30 seconds`.\n- The `work()` loop checks `expires_at` before processing a task. If `expires_at` is in the past, the task is considered unclaimed and is returned to `pending`.\n- A background thread (or a periodic check in `work()`) scans for expired claims and resets their state to `pending`.\n\n**Why 30 seconds?**\n- It is long enough for a worker to finish a typical task but short enough to recover quickly after a crash.\n- It balances the need for durability (tasks are not lost) with the need for responsiveness (workers can pick up tasks quickly).\n\n### Recovery after a crash\n\nIf the host process is killed (e.g., SIGKILL, power loss), the following happens:\n\n1. The SQLite database is left in a consistent state because all writes are atomic (SQLite uses WAL mode).\n2. On restart, `work()` will see any tasks that were claimed but not yet completed. Since they have expired, they will be returned to `pending`.\n3. The `dead` table will contain any tasks that have failed all retries, so they will not be retried.\n4. The `handlers` table will still have the registered handlers, so new tasks can be processed.\n\n**Guarantee**: No task will be lost. A task that has been acknowledged (i.e., claimed) will either be completed or will be retried. A task that has failed all retries will be marked as `dead` and will not be retried.\n\n## Failure Modes and How They Are Handled\n\n### 1. Task handler raises an exception\n**What happens**: The task is marked as `failed` and will be retried up to its `retry` count. After exhausting retries, it moves to `dead`.\n**Why**: This allows transient failures (e.g., network timeouts) to be retried while ensuring that persistent failures are not endlessly retried.\n\n### 2. Worker crashes while processing a task\n**What happens**: The task's claim expires after 30 seconds, and it is returned to `pending`. Another worker will pick it up.\n**Why**: This ensures that no task is stuck forever if a worker crashes.\n\n### 3. Database corruption\n**What happens**: SQLite will raise an error. The library will log the error and exit. The user will need to manually inspect the database or restore from a backup.\n**Why**: SQLite is robust, but we cannot guarantee absolute immunity to corruption. The design assumes that the underlying storage is reliable.\n\n### 4. Race condition: two workers claim the same task\n**What happens**: The claim is atomic (see \"Atomic claim\" below). Only one worker will succeed; the other will see that the task is already claimed and will skip it.\n**Why**: This ensures that no task is executed twice.\n\n### 5. Duplicate enqueue of the same logical job\n**What happens**: The enqueue operation checks if a task with the same `name` and payload is already pending or scheduled. If so, it does nothing.\n**Why**: This prevents duplicate work when the same logical job is enqueued twice by racing callers.\n\n### 6. Handler registration after tasks are enqueued\n**What happens**: The library will raise a `ValueError` if a task is enqueued for a name that has no registered handler.\n**Why**: This ensures that all tasks have a valid handler before they are processed.\n\n### 7. Scheduled task becomes ready while a worker is busy\n**What happens**: The task will be made visible to workers as soon as it becomes ready. Workers will pick it up in the next iteration.\n**Why**: This ensures that scheduled tasks are not delayed unnecessarily.\n\n## Trade-offs Rejected and Why\n\n### 1.
