Workers never hold locks on tasks they are processing; instead, they acquire a short-lived lease via an atomic UPDATE that both marks the task as \"running\" and assigns it a lease expiry timestamp. This lease mechanism ensures that if a worker crashes, the lease expires and the task becomes available again after a brief grace period.\n\n## Public API\n\n### `taskq.init(db_path: str, max_retries: int = 3, default_backoff_ms: int = 1000) -> None`\n\nInitializes the task queue, creating the database schema if it does not exist. When a handler raises an exception, the system determines whether it is transient or permanent:\n\n- **Transient**: The handler returns a dict with `\"retry\": true`. This is the only way to signal that the task should be retried.\n- **Permanent**: Any other outcome (including raising an uncaught exception) is treated as permanent failure.\n\nIf the task is marked transient, `retry_count` is incremented (capped at `max_retries`). The next available time is computed as:\n\n```\nnext_available_ms = scheduled_at_ms + (base_backoff_ms * 2^retry_count) + random(0, 500)\n```\n\nwhere `base_backoff_ms` is the `default_backoff_ms` config value (1000 ms by default) and the random jitter is up to 500 ms to spread load. If `scheduled_at_ms` is NULL (immediate task), the jitter is still applied relative to the current time.\n\nOnce `retry_count` reaches `max_retries`, the task is marked `status = 'failed'` and `next_available_ms` is set to a far future (e.g., `created_at_ms + 365 days`). The task remains queryable via `get_status` and `list_tasks`, but will never be picked up again automatically.\n\n## Crash Recovery\n\nCrash recovery relies on lease expiry. When a worker claims a task, it updates the row to `status = 'running'` and sets `lease_expires_at_ms` to `now + lease_duration_ms`. The lease duration is 30 seconds (30,000 ms).\n\nIf the worker crashes before completing the task, the lease expires. A background \"lease collector\" thread (started at initialization) runs every 5 seconds and scans for tasks where `status = 'running'` and `lease_expires_at_ms < now`. For each such task, it resets `status = 'pending'`, clears `lease_expires_at_ms`, and decrements `retry_count` (because the task was not retried, it should not count as a failed attempt). This ensures that no task is permanently stuck in the `running` state.\n\nThe lease collector is single-threaded and runs with a short sleep between scans to minimize CPU usage. It does not hold any locks on tasks; it only reads and writes the same atomic UPDATE used by workers, so concurrent lease resets are safe.\n\n## Failure Modes and Handling\n\n| Failure mode | Design response |\n|--------------|-----------------|\n| **Worker killed mid-task** | Lease expires after 30 s; task becomes `pending` again and can be re-claimed. |\n| **Database corruption** | SQLite with WAL mode and `PRAGMA journal_mode = WAL` ensures durability. On restart, the lease collector will clean up any orphaned `running` tasks. |\n| **Handler raises uncaught exception** | Treated as permanent failure; task is marked `failed` after `max_retries` attempts. Human must inspect via `list_tasks(status='failed')`. |\n| **Handler returns `retry: true` forever** | Capped by `max_retries`. After the cap, task is marked `failed`. |\n| **Multiple workers race to claim the same task** | The atomic `UPDATE ... WHERE status = 'pending'` ensures only one worker succeeds; others get no row to update and simply skip. |\n| **Scheduler delay overflows 32-bit int** | All timestamps are stored as 64-bit integers (Unix ms). Python's `sqlite3` module handles this transparently. |\n| **Config file missing on restart** | Hard-coded defaults (`max_retries = 3`, `default_backoff_ms = 1000`) are used. |\n\n## Trade-offs Rejected\n\n1. **Persistent worker leases (longer than 30 s)** – Rejected because longer leases increase the window during which a crashed worker could leave a task stuck. 30 s is a pragmatic balance between network latency and crash frequency.\n\n2. **Optimistic locking with retry on conflict** – Rejected because it would require workers to loop on `SELECT` + `UPDATE` and could starve other workers under high contention. The atomic `UPDATE` with `WHERE status = 'pending'` is simpler and scales well for the modest throughput target (hundreds per second).\n\n3. **Separate `tasks` and `task_instances` tables** – Rejected because it would complicate the lease collector and add unnecessary indirection. A single `tasks` table with `retry_count` and `lease_expires_at_ms` columns is sufficient.\n\n4. **Configurable lease duration per task** – Rejected because it would require per-task metadata and make the lease collector more complex. A uniform lease duration is adequate for the use case.\n\n5. **In-memory task cache** – Rejected because it would introduce inconsistency between cache and disk on crash. All state is persisted immediately.\n\n6. **Priority queues** – Out of scope per the spec; not implemented.\n\n7. **Task cancellation** – Out of scope per the spec; not implemented.\n\n8. **Web UI** – Out of scope per the spec; not implemented.\n\n---\n\nThis design satisfies all requirements in SPEC.md: atomic claiming, lease-based crash recovery, exponential backoff with jitter, human-inspectable failed tasks, and observability via status counts and listing.
