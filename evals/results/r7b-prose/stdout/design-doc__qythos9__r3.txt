It provides a simple API for enqueuing background work that survives process crashes, with built-in retry logic, scheduling, and duplicate prevention. The design targets modest throughput (hundreds of tasks/sec) and relies entirely on SQLite for persistence, with a single SQLite file shared by all workers in the process.\n\n**Core approach:**\n- **Single SQLite database** with a `tasks` table that tracks state (pending, running, failed, dead) and a `task_locks` table that provides atomic task claiming via a unique `lock_id`.\n- **Workers** are threads that loop: they atomically claim a task (INSERT INTO `task_locks` with a unique `lock_id`), run the handler, then either release the lock (on success) or re-queue (on failure).\n- **Crash recovery** is automatic: any task in `task_locks` that has no corresponding `task_id` in `tasks` (or whose `task_id` is in a terminal state) is re-queued as pending.\n- **Duplicate prevention** is achieved by a `task_id` that is a deterministic hash of (name, payload, scheduled_at). Must be called once before any other operation.\n\n**Returns:** `None`\n\n**Raises:** `sqlite3.Error` if the database cannot be created (e.g., permission denied).\n\n### `taskq.enqueue(name: str, payload: Any, scheduled_at: Optional[datetime] = None, retry_policy: Optional[RetryPolicy] = None) -> TaskId`\n\nEnqueues a new task. `name` identifies the handler (see below). `payload` must be JSON-serializable. `scheduled_at` may be `None` (run immediately) or a `datetime` in the future (run at that time). `retry_policy` is optional; if omitted, a default policy (max 3 retries, 1s base backoff) is used.\n\n**Returns:** `TaskId`, a unique integer identifier for the task (used for debugging and for `taskq.get_task`).\n\n**Raises:** `TypeError` if `payload` is not JSON-serializable; `ValueError` if `scheduled_at` is in the past.\n\n### `taskq.get_task(task_id: TaskId) -> Task`\n\nRetrieves a task by its ID. Example:\n\n```python\nRetryPolicy(max_attempts=5, base_delay=1.0, max_delay=60.0)\n```\n\n### `TaskId`\n\nAn `int` (the primary key in `tasks`).\n\n### `Task`\n\nA `NamedTuple` with fields `id`, `name`, `payload`, `scheduled_at`, `retry_policy`, `state`, `attempt`, `last_error`.\n\n### `Stats`\n\nA `NamedTuple` with fields `pending`, `running`, `failed`, `dead`.\n\n### `NotFoundError`, `AlreadyRegisteredError`\n\nCustom exceptions raised by the API.\n\n## Persistence Schema\n\n### `tasks` table\n\n| Column         | Type       | Description |\n|----------------|------------|-------------|\n| `id`           | INTEGER PK | Unique task identifier |\n| `name`         | TEXT       | Handler name (indexed) |\n| `payload`      | TEXT       | JSON-encoded payload (indexed) |\n| `scheduled_at` | TEXT       | ISO 8601 timestamp (indexed) |\n| `retry_policy` | TEXT       | JSON-encoded `RetryPolicy` (indexed) |\n| `state`        | TEXT       | `pending`, `running`, `failed`, `dead` (indexed) |\n| `attempt`      | INTEGER    | Number of retry attempts (indexed) |\n| `last_error`   | TEXT       | JSON-encoded last exception (indexed) |\n\n**Indexes:** `name`, `payload`, `scheduled_at`, `state`, `attempt`, `last_error`.\n\n### `task_locks` table\n\n| Column         | Type       | Description |\n|----------------|------------|-------------|\n| `lock_id`      | INTEGER PK | Unique lock identifier (indexed) |\n| `task_id`      | INTEGER FK | References `tasks.id` (indexed) |\n| `expires_at`   | TEXT       | ISO 8601 timestamp (indexed) |\n\n**Indexes:** `lock_id`, `task_id`, `expires_at`.\n\n**Invariant:** For every `lock_id`, there is exactly one `task_id`. A `task_id` may appear in multiple `lock_id`s only during the brief window when a worker has claimed it but not yet updated `tasks.state` to `running`. This is safe because the `task_locks` table is the source of truth for claiming; workers never read `tasks.state` directly for claiming.\n\n### `stats` table (optional, for fast queries)\n\n| Column         | Type       | Description |\n|----------------|------------|-------------|\n| `pending`      | INTEGER    | Count of `tasks.state = 'pending'` |\n| `running`      | INTEGER    | Count of `tasks.state = 'running'` |\n| `failed`       | INTEGER    | Count of `tasks.state = 'failed'` |\n| `dead`         | INTEGER    | Count of `tasks.state = 'dead'` |\n\n**Indexes:** none (small table, updated by a background thread after each state change).\n\n## Retries and Backoff\n\n**Policy:** When a handler raises an exception, `taskq` updates the task's `attempt` counter and `last_error`. If `attempt < retry_policy.max_attempts`, the task is re-queued with `state = 'pending'` and `scheduled_at = now + retry_policy.base_delay * (2 ** (attempt - 1))`, capped at `retry_policy.max_delay`.\n\n**Example:** `RetryPolicy(max_attempts=5, base_delay=1.0, max_delay=60.0)` yields delays of 1s, 2s, 4s, 8s, 16s (capped at 60s). After the fifth failure, the task is marked `state = 'failed'` and `last_error` is retained for inspection.\n\n**Rationale:** Exponential backoff with a cap prevents hammering a failing dependency while still providing rapid recovery for transient errors. The `max_delay` ensures that very long backoffs (e.g., 1 hour) do not cause indefinite stalls.\n\n**Alternative considered:** Fixed backoff (e.g., always 5s). Rejected because it either leads to thundering herd (if too short) or unnecessarily long waits (if too long). Exponential backoff is the standard for transient failures and matches the spec's requirement for \"back off\".\n\n## Crash Recovery\n\n**Scenario:** A worker crashes (SIGKILL, power loss) while a task is in `task_locks` (claimed but not yet updated in `tasks`). The `task_locks` entry has `expires_at = now + 30s` (see below).\n\n**Recovery steps (run by a background thread every 5s):**\n1. Scan `task_locks` for rows where `expires_at < now` **or** `task_id` is not present in `tasks` (or `tasks.state` is `failed`/`dead`).\n2. For each such row, delete the `task_locks` entry and update `tasks.state` to `pending`, reset `attempt` to 0, and clear `last_error`.\n3. This makes the task immediately re-claimable by any worker.\n\n**Claim expiration:** `expires_at` is set to `now + 30s` when a task is claimed. This ensures that a crashed worker will not hold a lock forever; after 30 seconds the lock is considered stale and the task is re-queued.\n\n**Why 30s?** It is long enough to survive a brief pause (e.g., a worker being killed and restarted) but short enough that a crashed worker will not block the queue for minutes. The background recovery thread runs every 5s, so the worst-case delay before a task becomes runnable again is ~35s, which is acceptable for the modest throughput target.\n\n**Alternative considered:** No expiration (rely on `task_locks` being deleted on crash). Rejected because a crashed worker could leave a `task_locks` row forever (e.g., if the OS does not clean up the file), causing the task to be permanently stuck. Expiration provides a safety net.\n\n## Failure Modes and Handling\n\n| Failure mode                              | Handling                                                                                                   |\n|------------------------------------------|-----------------------------------------------------------------------------------------------------------|\
